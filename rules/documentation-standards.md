# ドキュメント標準

## 目的

ドキュメントの情報アーキテクチャを定め、ナレッジの昇格パスを明確にする。

## 背景

AI エージェントとの協働で生まれるナレッジは、置き場を間違えると発見されない・重複する・古くなる。ディレクトリごとの責務と昇格パスを決めておくことで、情報の散逸を防ぐ。

既存の `document-consistency.md` は「コード変更とドキュメントの同期」に特化している。このルールは「ドキュメント全体の構造と知識の流れ」を扱い、並存する。

## ディレクトリ責務

プロジェクトの規模に応じて取捨選択する。小規模なら全部は要らない。`twin-soul` では `docs/` 配下ではなく、トップレベルの `rules/`、`specs/`、`decisions/` を使う。

### specs/

- 現行仕様、制約、API 仕様、参照用の事実
- 長い議論や採用理由は書かない（DR に寄せる）

### decisions/

- Decision Record（DR）
- Context / Decision / Consequences の構造
- specs の全文コピーではなく参照リンクを使う

### rules/

- 作業時に守るリポジトリ横断方針
- チェックリスト、禁止事項、推奨事項
- 現行仕様の説明や判断理由は主目的にしない

### バージョン管理外の作業領域

このリポジトリでは `memory/` を作業領域とする。gitignore 対象であり、共有の source of truth ではない。正は `rules/`、`specs/`、`decisions/` の適切な場所に寄せる。

- `memory/lessons.md` — 同じ過ちを繰り返さない学び
- `memory/handoff.md` — 進行中作業の申し送り
- `memory/notes/` — 作業用メモ、レビュー往復の生ログ、確立前の調査

運用は [`../AGENTS.md`](../AGENTS.md) の「作業メモリ」、雛形は [working-memory.md](working-memory.md) を見る。

## ナレッジ昇格パス

知識が生まれてから確立するまでの流れ。

```
Auto Memory（エージェントのセッション間自己学習）
    ↓ 共有すべき作業記録
memory/（一時的な記録）
    ↓ 解決策が確立
rules/、specs/、decisions/（正式ドキュメント）
    ↓ リポジトリ全体に影響する判断
DR（Decision Record）作成
```

### Auto Memory の位置づけ

- エージェントのセッション間自己学習（Claude Code 等の組み込み機能）
- 記録すべきもの: プロジェクト構造、既知の課題、確立したパターン
- 記録すべきでないもの: セッション固有の作業状態、未検証の仮説、正式ドキュメントと重複する内容

### 昇格の判断

- `memory/` にしかない知見で運用に効くものは要約して正式ドキュメントに昇格
- 昇格したら `memory/` の重複は削るか、正式ドキュメントへのリンクだけ残す
- 二重管理を避ける: 正は常に `rules/`、`specs/`、`decisions/` の適切な場所に寄せる

## レビュープロセス

### 修正ループ vs 分析ラウンド

- **修正ループ（最大 3 回）**: 修正 PR の往復。3 回修正しても解決しない場合はユーザーに報告
- **分析ラウンド（回数制限なし）**: 棚卸し・未解消整理・スキル適用報告など、PR 修正とは別工程。`memory/` の記録で区別する

### 別エージェントによるレビュー

- 対象: まとまった変更（複数ファイル、ドキュメントのみでも）
- 回数: 最大 3 回まで改善ループ
- 記録: 結果と未解消事項は `memory/` に残す
- 共有すべき結論だけを `rules/`、`specs/`、`decisions/` の適切な場所に昇格

## ドキュメント品質基準

### 必須

- **目的の明確化**: なぜこのドキュメントが必要か
- **対象読者の特定**: 誰が読むか

### 推奨

- 関連ドキュメントへのリンク
- 前提知識
- 読後に何をすべきか（次のステップ）
- 必要に応じた更新日の記載（時点依存の情報や外部仕様に依存する手順など）

### 避けるべき

- 同じ内容を複数箇所に書く（重複）
- 不確実な情報の断定（「仮説」と明記する）
- 更新されていない古い情報の放置

## 編集ルール

### specs の更新

1. まず source of truth（コード・設定・OpenAPI 等）を更新
2. 生成物があれば再生成
3. 手書きは補足に限定

### rules の更新

1. 作業時に守る方針として使える粒度にする
2. 現在仕様の長い説明は `specs/` へ逃がす
3. 判断理由や方針変更の履歴は `decisions/` へ逃がす

### decisions の更新

1. 新しい判断や方針変更は DR を追加
2. Accepted DR の意味変更は直接編集せず supersede
3. 軽微修正（誤字、表現調整）のみ直接編集可

### リンクの形式

- リポジトリ内は相対パスで指す
- 外部は公式 URL を優先
