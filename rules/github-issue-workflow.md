# GitHub Issue ワークフロー

## 目的

Issue の作成ルールとスコープ変更時の運用を定め、トレーサビリティを保つ。

## 背景

AI エージェントが Issue を作成する際、一時領域のパスを参照リンクに含めたり、スコープが大きく変わったのに同じ Issue を使い続けると、後から追跡できなくなる。実戦で磨かれたパターンをルールにする。

## バージョン管理外のパスを Issue に載せない

バージョン管理されていないファイルのパスを Issue の参照リンクに含めない。

**理由**: `memory/` はセッション固有の一時データであり、他の開発者がアクセスできない。Issue は長期間参照されるため、壊れるリンクを含めるべきでない。

**代わりに**: 正式な参照先（`rules/`、`specs/`、`decisions/`、`README.md` 等）を使う。

## Issue / PR の作成とコメント

Agent は Issue / PR 本文、コメント、PR description の下書きまでを基本とする。GitHub write は人間が確認して実行するか、GitHub Actions / GitHub App / executor などの分離された仕組みで扱う。

PR 本文の書式は [github-pr-workflow.md](github-pr-workflow.md) と [`.github/pull_request_template.md`](../.github/pull_request_template.md) に従う。

Agent が読めるローカル shell に GitHub write token を置いて `gh` を直実行させる運用は標準案内しない。判断理由は `decisions/0007-withdraw-local-gh-agent-write.md` を参照する。

## スコープ変更時の運用

調査や議論の結果、Issue の問題理解やスコープが大きく変わった場合:

1. **新しい Issue を作成**: 調査結果を背景に含め、更新されたスコープで作成
2. **旧 Issue をクローズ**: 新 Issue へのリンクと、スコープ変更の理由をコメントに記載
3. **リンクの双方向化**: 新 Issue の背景に旧 Issue 番号を記載し、トレーサビリティを確保

### 判断基準

以下のいずれかに該当する場合はスコープ変更とみなす:

- 技術調査の結果、前提が変わった
- やることリストの半分以上が変わった
- 成果物の種類が変わった（例: ドキュメントのみ → コード変更 + ドキュメント）

### やらないこと

- 旧 Issue のタイトル・本文を大幅に書き換えて再利用する（履歴が追いにくくなる）

## 記載ガイドライン

### 背景

- なぜこのタスクが必要かを簡潔に説明
- 現状の課題や問題点を具体的に記載

### 目的

- 期待する成果を明確に記載
- 曖昧な表現を避け、完了条件が分かるように

### やること

- チェックリスト形式（`- [ ]`）を使う
- 作業項目は具体的かつ実行可能な粒度
- 必要に応じてサブタスクをネスト

### 参考リンク

- 関連する DR、仕様書へのリンク（リポジトリ内は相対パス）
- 外部ドキュメントは公式 URL を優先
