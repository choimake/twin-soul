# multi-model-debate の設定を YAML にし、議論役の呼び出しを同梱スクリプトで時間の上限付きにする

## ステータス

採用済み (2026-11-01)

## 背景

`decisions/0013-use-root-config-file-for-multi-model-debate.md` で、席とラウンド数の上限を利用先のルートの `.multi-model-debate.md` に書くことにした。書く中身は席の一覧と数値だけで、自然言語の説明は要らない。

議論役の呼び出しの時間の上限は、SKILL.md に「最後は強制終了まで行う」と書き、止め方の実装はオーケストレーターに任せていた。実際に 8 ラウンドの議論を回したとき、次のことが起きた。

- オーケストレーターが SIGALRM を 1 回送るだけの実装にした。agy は回答を出し終えたあとも終了せず、SIGALRM を無視して 75 分残った
- agy のログでは、回答を出し終えて会話を閉じたあと、バックグラウンドのサーバーが残って数分おきにモデル一覧を取りに行っていた。TERM を受けても終了処理の途中で止まり、KILL で終わった
- 回答にかかった時間は、どの席も 3 分ほどまでだった。居座りは 8 ラウンド中 3 回起きた（3 分、75 分、13 分）

変更前の SKILL.md のまま、別のエージェント（Opus と Sonnet）に、回答後に TERM を無視して居座る偽の CLI で議論を回させると、どちらも KILL まで実装して最後まで終えた。止め方を毎回エージェントに書かせると、書けることもあれば書けないこともある。

## 検討した選択肢

設定ファイルの形式:

- Markdown（0013 のまま）
  - 良い点: `.decision-records.md` と同じ形
  - 悪い点: 中身は席と数値だけで、文章が要らない
- YAML
  - 良い点: 席と数値をそのまま書ける。元の `config/defaults.yaml` と同じキーを使える

止め方:

- SKILL.md の文章を詳しくする
  - 悪い点: 毎回エージェントが実装する限り、ばらつきは残る
- 止める処理をスクリプトにして skill に同梱し、各席をそれ経由で呼ばせる
  - 良い点: 止め方が毎回同じになる。自己テストで止まり方を確かめられる
  - 悪い点: スクリプトを使わずに呼ぶエージェントは止められない
- 作業者のメモに残すだけ
  - 悪い点: その作業者の環境でしか効かない

時間の上限の決め方:

- 全体の上限だけ
  - 悪い点: 回答を出し終えて居座るツールを、上限まで待つことになる
- 全体の上限に加えて、出力が止まったら回答を出し終えたとみなして止める
  - 良い点: 居座るツールでも、回答を出し終えてから一定時間で次へ進める

## 判断

- 設定ファイルは `.multi-model-debate.yaml` にする。自然言語が要らないため。キーは `seats`、`max_rounds`、`timeout_sec`、`idle_sec`
- 各席は、skill に同梱した `scripts/run-seat.py` を通して呼ぶ。全体の上限を過ぎるか、出力が止まってから決めた秒数が過ぎると、プロセスグループごと TERM を送り、残っていれば KILL する
- 時間の上限は設定ファイルで変えられる。全体の上限の既定は 10 分にする。回答にかかった時間が最大 3 分ほどだったため。出力が止まってからの秒数の既定値は、実装を正とする

## 影響

メリット:

- 回答を出し終えても終了しないツールがあっても、議論が止まらない
- 環境に合わせて時間の上限を変えられる

デメリット:

- 出力が止まったら終わりとみなすので、途中で長く黙るツールは、回答の途中で止められることがある。止めた席は、指示した見出しが最後まで出ているかを見て、出ていなければ失敗として扱う
- 0013 で `.multi-model-debate.md` を置いた環境は、`.multi-model-debate.yaml` に書き直す必要がある
