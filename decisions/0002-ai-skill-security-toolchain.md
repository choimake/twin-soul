# AI スキルセキュリティ検証ツールチェーンの選定

## ステータス

置き換え先: [0003](0003-deprecate-ai-skill-security-toolchain.md) (2026-04-20)

当初は採用済み (2026-03-21)。

## 背景

ブラックボックスな AI スキル（他人が作成したプロンプトや実行コード）を、目視チェックなしで自社開発環境やプロダクトに統合する際、以下のセキュリティリスクがある：

- プロンプトインジェクション（命令上書き）
- 不正なコード実行
- 機密情報の漏洩

これらを自動検知する必要があり、当初は promptfoo、garak、E2B の組み合わせを検討したが、運用中に以下の問題が判明した：

- garak は依存関係が重く、Ollama 連携が不安定
- Ollama の重いモデル（qwen3:30b）はローカルマシンに負荷が高い
- 軽いモデル（llama3.2, qwen2.5:7b）は日本語でのセキュリティテストで精度不足

検証の結果、llama3.2 は 81.82% の成功率で閾値 80% をギリギリクリアしたが、多段階攻撃には脆弱であることが確認された。より高い安全性と日本語対応を両立するため、ツールチェーンを見直した。

検討したが採用しなかった選択肢：

- **OpenAI/Anthropic API**: 高精度だが API 費用と機密情報の外部送信が課題
- **カスタムセキュリティスキャナー**: 開発・メンテナンスコストが高い
- **garak**: 依存関係が重い、Ollama 連携が不安定、promptfoo で十分
- **Ollama**: mlx-lm に置き換え（Apple Silicon 最適化のため）

## 判断

以下のツールチェーンを採用する：

1. **promptfoo** (セキュリティ検証の中核、80%)
   - プロンプトインジェクション耐性の定量評価
   - OWASP LLM Top 10 対応
   - 自動レッドチーミング

2. **E2B** (コード実行検証、20%)
   - 隔離された使い捨てサンドボックス
   - コード実行を伴う `skill` の検証

3. **mise** (環境管理)
   - Node.js、Python を一括管理
   - Mac/Linux の環境差異を吸収

4. **mlx-lm + Qwen（4bit MLX 版）** (推論エンジン)
   - Apple Silicon 最適化のローカル LLM（無料、プライバシー確保）
   - OpenAI 互換サーバーで promptfoo と簡単に統合
   - 日本語に強く、セキュリティテストに適したサイズ感（モデルはリポジトリのデフォルトに追随）
   - **検証結果 (2026-03-21、当時のデフォルト Qwen3.5-9B-4bit)**: 100% (11/11) の成功率で全テストケース合格
     - アサーション改善後、DAN 攻撃、SQL インジェクション、多段階攻撃を含む全攻撃パターンを正しく拒否
   - **更新 (2026-03-29)**: リポジトリのデフォルトを **Qwen3.5-4B-4bit** に変更（VRAM・速度優先）。`MLX_LM_MODEL` で上書き可能。上記 100% は 9B における記録であり、4B では再計測が必要。

## 影響

- promptfoo + mlx-lm でシンプルに運用可能
- ローカル完結（API 費用ゼロ、機密情報が外部に出ない）
- 当時の Qwen3.5-9B-4bit で日本語プロンプトインジェクション攻撃を 100% 検知（記録）。デフォルト 4B への変更後は再計測すること
- mise による環境管理で再現性が高い
- Apple Silicon 最適化により高速な推論が可能
- mlx-lm は Mac 専用のため、CI 環境では別の推論エンジンが必要
- promptfoo のバージョン管理が必要（頻繁にアップデートされる）
- ローカル LLM の精度が OpenAI/Anthropic API より低い可能性（ただし現時点で実用レベル）
- promptfoo の設定をメンテナンスし、新しい攻撃パターンに対応する必要がある
- CI 環境では OpenAI API の代替手段または Linux 用推論エンジンの導入が必要
- アサーション設計が重要: モデルが攻撃を正しく拒否していても、拒否の説明に攻撃内容を引用すると `not-icontains` で失敗する（`icontains-any` で拒否の意思を確認する方が実用的）
