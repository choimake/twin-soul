# `skills` を外部展開単位とし、`specs` と `decisions` を内部文書として扱う

## ステータス

採用済み

## 背景

`twin-soul` では `skills/`、`rules/`、`specs/`、`decisions/` を同じリポジトリに置いているため、どのドキュメントや資産を外部プロジェクトへ持ち出す前提で扱うのかが会話中にずれやすかった。

特に、`skill` の設計相談で `specs/` や `decisions/` を前提に説明すると、利用先プロジェクトでもそれらが参照できる前提に見えてしまう。一方で、このリポジトリのインストーラーと現在の運用は `skills/` を外部展開単位として扱っている。

このずれを防ぐため、外部へ持ち出す資産と `twin-soul` 内部のドキュメントを明確に分けて記録しておく必要がある。

## 判断

`twin-soul` では、ドキュメントと資産の境界を次のように扱う。

- `skills/` は外部プロジェクトへ単体で展開できる資産とする
- `skill` は、利用先リポジトリに `specs/` や `decisions/` が存在しない前提でも機能するように保つ
- `specs/` は `twin-soul` 自身の構成、運用、配布方針を整理する内部ドキュメントとして扱う
- `decisions/` は `twin-soul` 内部の判断理由と方針変更履歴を残す内部ドキュメントとして扱う
- `rules/` は位置づけを確定していないため、当面は外部展開の主役として扱わない

`skill` の設計や改稿では、まず `skill` 単体で成立するかを確認し、内部ドキュメントへの依存を増やさないことを優先する。

## 影響

メリット:

- `skill` の責務が明確になり、外部プロジェクトへ導入しやすくなる
- `specs/` と `decisions/` を `twin-soul` 内部の整理と意思決定に集中させられる
- 会話中に内部ドキュメントを前提にしすぎるコンセプトずれを防ぎやすい

デメリット:

- `skill` に必要な文脈は `skill` 自身か配布される補助ファイルに含める必要がある
- `rules/` をどう扱うかは別途判断が必要なまま残る

影響:

- `specs/` には `twin-soul` の内部運用や構造境界を書く
- `decisions/` には境界変更や方針変更の理由を書く
- `skills/` の新規作成や改稿では、外部展開可能性を確認項目に含める
