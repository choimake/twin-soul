# Gap 分析 判断知識

skill 試行・品質確認用の依頼例: [../assets/test-prompts.md](../assets/test-prompts.md)

## 対象と探索の絞り方

対象 PRD または検証の範囲が不明なときは、最小限の確認質問だけを返し、本文生成には入らない。

## 要件の区切り方（ID は任意）

- **連番 ID（例: T-01）やチケット番号は必須にしない**。入力側に無い場合は新規に付与しない
- ID が無い場合は、`### 〈短いラベル〉` のような見出し、またはグループ直下の箇条書きで要件を区切る
- サマリ表の「要件」列は、**既存 ID があればそれを使い、無ければ短いラベル**でよい

## 判定凡例（既定）

次の三値を既定とする。プロジェクトで別名を使う場合は、ドキュメント冒頭の凡例表で定義を書き換える。

| 判定       | 意味                                                                               |
| ---------- | ---------------------------------------------------------------------------------- |
| 可         | 実測または仕様確認で、制約なく要件を満たせる                                       |
| 条件付き可 | 実現は可能だが、制限・前提・追加設計が必要                                         |
| 不可       | 仕様・契約・技術上、要件を満たせない（エラー実測や公式ドキュメント上の制約を含む） |

未検証は三値の溢れ用である。判定欄に書いてよいが、凡例の三値には加えない。

### 条件付き可 と 可 の見分け

- **可**: 制限が「運用上の注意」程度で、PRD の達成を阻害しない
- **条件付き可**: 代替手順・追加コスト・別コンポーネント前提・仕様変更検討が読者に伝わるべきとき

## 証拠の梯子

自己申告の文章は根拠にしない。文章は手がかりであり、判定の根拠は到達した証拠レベルである。未証明を「可」に丸めない。

各要件の「証拠レベル」行に、到達した一番上のステップと、読者が辿れるポインタ（パス・行・URL・コマンド出力）を書く。

| レベル | 名前     | 何が揃っているか                         | 可にしてよいか                         |
| ------ | -------- | ---------------------------------------- | -------------------------------------- |
| 1      | 言った   | 自己申告・要約だけ                       | しない。常に未検証                     |
| 2      | file:line | 実ファイルの行、または公式 docs の URL | 仕様・契約・quota なら可の下限。振る舞いは未検証または条件付き可 |
| 3      | 経路     | 失敗がその箇所に届かないことを手順で辿った | 条件付き可まで。振る舞いで可にするには足りない |
| 4      | 実行     | 実コード・実 API・コマンドの出力         | 振る舞い要求の可の下限                 |
| 5      | 本番相当 | 実行中アプリや検証環境での再現           | 可の最強                               |

要件種別の見分け:

- **仕様・契約**: quota、API の公式制約、契約条項。机上の確認で足りる。`file:line` または公式 URL が可の下限
- **振る舞い**: 実際の応答、副作用、画面、ネットワーク。実行が可の下限

レビュー担当が「可」と書いただけではレベル 1 である。レビューを根拠にするなら、その指摘が指す `file:line` かコマンド出力まで梯子を進める。

言っただけの例:

- 「調査の結果、満たせる」
- 「仕様上問題ないはず」
- ログも行番号も無い厚いメモ

未検証にするとき:

- 実現可否列に **未検証** と書く
- 根拠列に、足りない証拠の種類（実測、API 応答、ドキュメント条項など）を書く
- 推測なら推測だと書き、断定しない

## 品質チェック（簡易）

- 判定凡例が読者向けに定義されている
- 各要件に、PRD 側の記述と、証拠に基づく判定が対になっている
- 各要件に証拠レベルがあり、ポインタが辿れる
- 可なのに梯子が無い、または言っただけで可、になっていない
- 条件付き可・不可には、制限または理由が根拠列または制限事項に書かれている
- サマリが本文と矛盾していない

## 出力モードごとの期待

### `review`

- ドキュメント構成（必須ブロックの欠落）、判定と根拠の対応、証拠不足の指摘
- 可なのに証拠レベルが無い、言っただけで可、仕様確認なのに `file:line` も公式 URL も無い、を指摘する
- 全文の書き直しは求められていなければ、修正提案に留める

### `draft`

- 先に対象範囲・判定凡例・要件の区切り方（ID 有無）を短く要約する
- 続けて [assets/gap-analysis-template.md](../assets/gap-analysis-template.md) の章立てを省略せず、プレースホルダを埋めた、保存できる Markdown 本文を返す

### `write-file`

- 書き込み後、保存先と要約（要件数・判定内訳・未検証の有無）を短く報告する
