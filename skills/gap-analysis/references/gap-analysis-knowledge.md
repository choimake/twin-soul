# Gap 分析 判断知識

この資料は `gap-analysis` skill の判断知識をまとめたものである。`SKILL.md` は使い方に留め、詳細判断はこの資料とテンプレートを起点にする。

テンプレート:

- [../assets/gap-analysis-template.md](../assets/gap-analysis-template.md)
- [../assets/requirement-row-template.md](../assets/requirement-row-template.md)
- [../assets/test-prompts.md](../assets/test-prompts.md)（skill 試行・品質確認用）

## この skill の役割

- PRD（または同等の要求一覧）と、検証・調査で得た**証拠**を対応づけ、実現可否と影響を表にまとめる
- 本 skill は **PRD と証拠の突合表** に限定する。バックログアイテム本体（ユーザーストーリー・受入基準の起案）や、実装手順・変更ファイル一覧を主とする計画書は対象外として切り分ける

## 呼び出し側が渡せる入力

- 対象 PRD または要件リスト（テキスト・`@path`）
- 検証メモ、ログ要約、環境名、検証期間
- 既存 Gap 分析ドキュメントの `@path`（レビュー時）
- 出力モード: `review` / `draft` / `write-file`
- 保存先ファイルパス（`write-file` 時）

未指定なら、会話から妥当な既定値を判断する。必要最低限の確認だけを追加する。別 skill の実行を要求しない。

出力モードの既定値:

- 既存の Gap 分析ドキュメントの `@path` が渡されている → `review`
- 新規下書きの依頼 → `draft`
- 保存先パスが明示され、ファイル作成を依頼された場合のみ `write-file`

## 対象と探索の絞り方

1. ユーザーが `@path` で PRD または既存 Gap 分析ドキュメントを指定したら、その対象を中心に扱う。
2. `review` / `draft` / `write-file` が明示されていればそれを優先し、未指定なら依頼文から推定する。
3. 対象 PRD、検証範囲、検証期間、環境のいずれかが不明なときは、最小限の確認質問だけを返し、本文生成には入らない。
4. 境界にあたる依頼（バックログアイテムの起票そのもの、実装手順中心の計画書作成）は対象外として切り分ける。

## 要件の区切り方（ID は任意）

- **連番 ID（例: T-01）やチケット番号は必須にしない**。入力側に無い場合は新規に付与しない
- ID が無い場合は、`### 〈短いラベル〉` のような見出し、またはグループ直下の箇条書きで要件を区切る
- サマリ表の「要件」列は、**既存 ID があればそれを使い、無ければ短いラベル**でよい

## 判定凡例（既定）

次の三値を既定とする。プロジェクトで別名を使う場合は、ドキュメント冒頭の凡例表で定義を書き換える。

| 判定       | 意味                                                                               |
| ---------- | ---------------------------------------------------------------------------------- |
| 可         | 実測または仕様確認で、制約なく要件を満たせる                                       |
| 条件付き可 | 実現は可能だが、制限・前提・追加設計が必要                                         |
| 不可       | 仕様・契約・技術上、要件を満たせない（エラー実測や公式ドキュメント上の制約を含む） |

### 条件付き可 と 可 の見分け

- **可**: 制限が「運用上の注意」程度で、PRD の達成を阻害しない
- **条件付き可**: 代替手順・追加コスト・別コンポーネント前提・仕様変更検討が読者に伝わるべきとき

### 証拠が不足しているとき

- 実現可否列に **未検証** や **要追加検証** と明記し、根拠列に不足している証拠の種類（実測、API 応答、ドキュメント条項など）を書く
- 推測のみの場合は推測であることを明記し、断定を避ける

## 各要件ブロックの列（既定）

1 要件あたり、次の行を持つ表を既定とする（テンプレート参照）。

- PRD 要件
- 実現可否
- 根拠・実証内容
- 制限事項
- 代替案・回避策
- PRD 仕様変更案

「共通前提・制約」に長い比較表や前提説明を置いてもよい（任意）。

## 品質チェック（簡易）

- 判定凡例が読者向けに定義されている
- 各要件に、PRD 側の記述と、証拠に基づく判定が対になっている
- 条件付き可・不可には、制限または理由が根拠列または制限事項に書かれている
- サマリが本文と矛盾していない

## 出力モードごとの期待

### `review`

- ドキュメント構成（必須ブロックの欠落）、判定と根拠の対応、証拠不足の指摘
- 全文の書き直しは求められていなければ、修正提案に留める

### `draft`

- 先に対象範囲・判定凡例・要件の区切り方（ID 有無）を短く要約する
- 続けて [assets/gap-analysis-template.md](../assets/gap-analysis-template.md) の章立てを省略せず、プレースホルダを埋めた file-ready な Markdown 本文を返す
- 1 要件だけ詳しく書く依頼なら [assets/requirement-row-template.md](../assets/requirement-row-template.md) を単体で使ってよい

### `write-file`

- ユーザーが保存先パスを明示したときのみ、該当パスにファイルを書く
- 書き込み後、保存先と要約（要件数・判定内訳・未検証の有無）を短く報告する
- パス未指定なら `draft` にフォールバックする

## 応答時の明示事項

- 対象が曖昧なときは、PRD の範囲・検証の範囲・既存ドキュメントの有無を短く確認してから本文生成に入る
- 対象が決まったら、関係する既存 Gap 分析ドキュメントとこの `references/` のみを参照すると添える

## `scripts/` を追加しない判断をした理由

- テンプレートと判断凡例で運用でき、壊れやすい自動処理が無い
- 繰り返しの整形・検証が必要になった時点で、改めて追加を検討する
