# テスト生成

この資料は `testcode` skill の `generate` 観点をまとめたものである。テスト本文をいきなり書く前に、対象理解とケース整理を入れるための判断材料として使う。

## 生成フロー

テスト生成は、次の順で進めるほうが安定する。

1. 対象コードの責務、入出力、例外、状態変化を説明する
2. 正常系、境界値、異常系、外部依存に分けてケースを列挙する
3. ケースが足りなければ、空入力、最小値、最大値、不正値、重複、順序違い、タイムゾーンやロケール依存などを追加で掘る
4. 足さない 3 種に当たるケースは捨てる
5. その後で、保存できる形のテスト本文へ落とす

## 足さない 3 種

通るが弱いテストを足すくらいなら、テストを増やさない。代わりに既存テストや手動の確認手順を短く返す。

- **モックばかり**: 検証の主眼が、自分が用意した偽物の戻り値である。依存の呼び出し順だけを見ている。本物の契約を何も固定していない
- **実装の鏡**: 内部の呼び出し順、private な手順、一時変数を写している。利用者から見える振る舞いがない。詳細は [tests-express-what.md](tests-express-what.md)
- **タイミング依存**: `sleep`、壁時計、実行順、共有のグローバル状態に頼る。同じ条件で毎回同じ結果にならない

smell 名のカタログは [test-smells.md](test-smells.md) を見る。generate では上記 3 種を拒否するだけにする。

## ケース整理の観点

- 正常系:
  - 期待通りの入力で主な振る舞いが通るか
- 境界値:
  - 最小値、最大値、ゼロ、空文字、空配列、しきい値ちょうどを見ているか
- 異常系:
  - 無効入力、型違い、例外、失敗戻り値を見ているか
- 外部依存:
  - 時刻、乱数、ファイル、DB、ネットワーク、環境変数の影響をどう切り離すか
- 状態遷移:
  - 呼び出し前後で状態や副作用が変わるなら、その変化を確認しているか

## 生成時の注意

- 単純な関数でも、境界値や例外処理を先に列挙しないと「通るが弱い」テストになりやすい
- 既存テストがある場合は、何を既に保証しているかを見て重複を避ける
- テスト用の共通部品を増やしすぎると、かえってテストの意図が見えにくくなる
- 実装詳細に強く結びついた assertion より、利用者視点の振る舞いを優先する。テストが示す層は振る舞いとする。詳細は [tests-express-what.md](tests-express-what.md) を参照する

## `generate` の進め方

1. 対象コードの責務と入出力を言語化する
2. 正常系、境界値、異常系、外部依存、状態遷移を分けてケース候補を出す
3. 既存テストがあれば重複を避ける
4. 足さない 3 種に当たるケースは捨て、テストを増やさない。代わりの検証を短く返す
5. テストフレームワークの慣習に沿って、保存できる形の本文へ落とす
6. 可能ならテスト用の共通部品を増やしすぎず、読みやすい単位で分ける
