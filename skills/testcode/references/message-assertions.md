# メッセージのアサート

この資料は、エラー・ログ・例外メッセージの検証方針をまとめる。メッセージが仕様の一部なら、テストから最終的な出力を読める形で検証する。

## 基本方針

メッセージは完全一致でアサートする。

- メッセージ本文への `in`、`contains`、`match=`、緩い正規表現での部分照合を避ける
- 期待文字列はテストにリテラルで書く
- プレフィックス、区切り、フィールド構造、末尾の句読点まで含める
- 複数メッセージが出る場合も、個々の要素は完全一致で比較する

例:

```python
with pytest.raises(ValueError) as exc_info:
    parse_user_id("abc")

assert str(exc_info.value) == "Invalid user_id: expected integer, got 'abc'"
```

複数メッセージの例:

```python
messages = [call.args[0] for call in logger.warning.call_args_list]

assert "retry scheduled: attempt=2 backoff=4s" in messages
```

この例では `in messages` を使っているが、比較対象の要素は完全なメッセージ文字列である。`"backoff=4s" in message` のような部分一致にはしない。

## 動的値の扱い

テスト入力で決定する値は、確定値として全文に含める。

- backoff 値
- ID
- 件数
- phase 名
- retry 回数
- 入力値やフィールド名

例:

```python
assert message == "[phase=sync] retry scheduled: account_id=acct_123 attempt=3 backoff=8s"
```

タイムスタンプ、乱数、一時ファイルパスなど、テスト内で固定できない値だけを正規化または分離する。

```python
assert normalize_timestamp(message) == "[created_at=<timestamp>] imported 3 records"
```

非決定な断片を理由に、決定的な断片まで部分一致にしない。

## `match=` と正規表現

pytest の `match=` は正規表現検索であり、全文のリテラル比較ではない。例外メッセージを仕様として固定したい場合は、例外を捕捉して `str(exc_info.value) == ...` のように比較する。

正規表現を使うのは、次のような場合に限る。

- 真に非決定な断片だけを別表現にしたい
- 外部ライブラリ由来で全文を仕様にできない
- テスト対象が正規表現そのものを出力仕様としている

その場合も、`^...$` や正規化済み文字列との比較を使い、どこまでを仕様として読むべきかを明確にする。

## 部分一致を避ける理由

部分一致は、メッセージ仕様の回帰を見逃しやすい。

- `: ` 区切りが消えても通る
- `[phase=...]` のようなプレフィックスが消えても通る
- フィールド順や区切り文字が変わっても通る
- 余計な補足文や誤った ID が混ざっても通る

結果として、テストから「最終的に何が出力されるか」が読めなくなる。複数の曖昧な assertion が並ぶと、失敗時に何が壊れたかも分かりにくくなり、`Assertion Roulette` につながる。

## 例外

全文一致を使うのは、プロジェクト側が生成し、出力仕様として意味があるメッセージに限る。

次のメッセージは、型・コード・構造化フィールドなど、より安定した値で検証する。

- 外部ライブラリが生成するメッセージ
- OS や実行環境で変わるメッセージ
- ローカライズ対象の文言
- 人間向け説明で、仕様として固定していない文言

ただし、ユーザーに表示する文言、ログ監視で拾う文言、運用手順に載る文言は仕様になりやすい。その場合は全文を固定する。
