# 検証手順が具体的か

## ねらい

検証手順が無いと、「実装が完了したかどうか」を確認できない。
コマンド例と期待結果を明示することで、実装者とレビュアーが同じ基準で検証できる。

## チェック観点

- 検証セクションが存在するか
- 各検証項目に **コマンド例** が含まれているか
- 各検証項目に **期待結果** が含まれているか
- 「確認する」だけの曖昧な表現になっていないか

## 指摘する基準

- 検証セクションが無い、または空の場合は **重大** として指摘する
- コマンド例が無い、または「確認する」だけの曖昧な表現の場合は **重大** として指摘する
- 期待結果が不明確な場合は **提案** として指摘する

## 例

### 悪い例（曖昧すぎる）

```markdown
## 検証

- ファイルが作成されたことを確認する
- テストが通ることを確認する
```

### 良い例（コマンド例と期待結果が明確）

````markdown
## 検証

### 構造チェック

\```bash

# ディレクトリ構造が正しいことを確認

ls -la skills/planner/
ls -la skills/planner/assets/
ls -la skills/planner/references/
\```

期待結果: `SKILL.md`, `assets/`, `references/` が存在する

### 動作テスト

\```bash

# Claude Codeで /planner コマンドを実行

/planner draft --task "新機能の追加"
\```

期待結果: plan fileが生成され、必須セクション（背景, 目的, 受け入れ条件, ベストプラクティス, 検証）が含まれる
````

## 補足

- 検証手順は「実装者が自己チェックできる」レベルの具体性を持つ
- コマンド例はコピペで実行できる形式が望ましい
- 期待結果は「何が確認できれば OK か」を明示する
