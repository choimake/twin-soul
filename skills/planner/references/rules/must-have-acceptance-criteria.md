# 受け入れ条件が明確に定義されているか

## ねらい

受け入れ条件が無いと、「何ができたら完成か」が曖昧になり、実装フェーズで手戻りが発生する。
検証可能な条件を明示することで、実装者とレビュアーの認識を揃える。

## チェック観点

- 受け入れ条件セクションが存在するか
- 各条件が **検証可能** か（曖昧な表現ではなく、具体的なチェック項目）
- 前後比較（減った・短くなった）を条件にする場合、比較前の実測が書かれているか。絶対閾値は対象外
- チェックボックス形式で記述されているか

## 指摘する基準

- 受け入れ条件セクションが無い、または空の場合は **重大** として指摘する
- 条件が曖昧すぎる（例: "うまく動く"、"良い感じになる"）場合は **重大** として指摘する
- 前後比較だけの条件で、比較前の実測が無い場合は **重大** として指摘する
- チェックボックス形式ではない場合は **提案** として指摘する

## 例

### 悪い例（曖昧すぎる）

```markdown
## 受け入れ条件

- 機能が動く
- テストが通る
```

### 良い例（検証可能）

```markdown
## 受け入れ条件

- [ ] `skills/planner/SKILL.md` が作成され、目的 / 使う場面 / 手順 / 期待する出力 / 検証 の5セクションを含む
- [ ] `skills/planner/assets/plan-template.md` が作成され、必須セクション（背景, 目的, 受け入れ条件, ベストプラクティス, 検証）を含む
- [ ] `apm install --dry-run --target cursor,claude` で `skills/planner` が導入対象として検証されることを確認
```

## 補足

- 受け入れ条件は「実装者が何を作ればよいか」と「レビュアーが何を確認すればよいか」の両方を明確にする
- 条件は具体的なファイル名、コマンド、期待結果を含むことが望ましい
- チェックボックス形式（`- [ ]`）を使うと、進捗追跡がしやすい
