# スコープが明確か

## ねらい

スコープが曖昧だと、「何を作るのか」「何を作らないのか」が不明確になり、実装範囲が膨らむ。
明確なスコープ定義で、実装者が迷わず進められるようにする。

## チェック観点

- 目的セクションに「達成したいこと」が明確に書かれているか
- 実装方針に「やること」と「やらないこと」の境界が見えるか
- 変更対象ファイルで変更対象ファイルが特定されているか
- スコープ外の作業が明示されているか（必要に応じて）

## 指摘する基準

- 目的セクションが無い、または「良い感じにする」のような曖昧な表現の場合は **重大** として指摘する
- 実装方針が大雑把すぎる（Phase 分けが無い、ステップが 1〜2 個だけ）場合は **提案** として指摘する
- スコープ外の作業が曖昧な場合は **提案** として指摘する

## 例

### 悪い例（曖昧すぎる）

```markdown
## 目的

planner skillを追加する

## 実装方針

1. ファイルを作る
2. テストする
```

### 良い例（スコープが明確）

```markdown
## 目的

plan作成プロセスを支援する汎用skillを追加し、以下を実現する：

1. **必須項目の強制**: 受け入れ条件、ベストプラクティス参照、検証手順を必ず含める
2. **AI自動レビュー**: ルールベースでplan fileを自動チェックし、不合格なら修正を促す
3. **柔軟な保存先**: 保存先を明示した場合のみ任意パスに保存可能
4. **Web検索統合**: タスク内容から自動的にベストプラクティスを検索し、planに組み込む

## 実装方針

### Phase 0: skill-creator による初期構造作成

1. `/skill-creator` を呼び出し、`planner` skillの初期構造を作成
2. skill-creatorが生成した構造を確認し、必要に応じて調整

### Phase 1: テンプレートとレビュールールの詳細化

1. `skills/planner/assets/plan-template.md` を作成
2. `skills/planner/assets/review-output-template.md` を作成
```

## 補足

- スコープは「達成したいこと」と「達成しないこと」の両方を明確にする
- Phase 分けは 3〜5 個程度が適切（多すぎると細かすぎる、少なすぎると大雑把）
- 変更対象ファイルで変更対象ファイルを列挙することで、スコープが具体化される
