# 方法論相談と実装 plan が分離されているか

## ねらい

「方針どう思う」「どっちがいい？」系の依頼を、いきなり実装 plan に落とすと手段比較だけが先行し、Why や成立条件が抜ける。方法論フェーズの成果物と実装フェーズの plan を混同しない。

## チェック観点

- 依頼が相談・方法論整理系か、実装 plan 作成系かが plan 冒頭で明示されているか
- 相談系の場合、**Why・背景・制約** が記述の前提として揃っているか
- 成果物が (1) 現状調査 → (2) 方法論・成立条件・限界・前提 → (3) 記録 の流れになっているか
- **実装 plan・変更ファイル一覧・実装検証手順** がスコープ外であると本文で明示されているか
- 実装フェーズへの言及は「次フェーズで planner / 実装者が扱う」等と分離されているか

## 指摘する基準

- 相談系なのに実装 plan テンプレ（変更対象ファイル、実装方針の詳細）だけが書かれ、調査・方法論が欠けている場合は **重大**
- Why・背景・制約が未記載のまま手段比較だけが進んでいる場合は **重大**
- 方法論相談なのに実装スコープ外の明示が無い場合は **提案**
- 変更対象ファイルの具体パスが **3 件以上**、または Phase 1 以降の実装ステップが **3 件以上** 列挙されている場合は **実装 plan 扱い** に切り替える（方法論ラベルでも `files-are-identified.md` 等の適用外を解除）
- 記録（issue コメント / DR ドラフト / plan の調査・方針節）までで止まっており、実装詳細に踏み込んでいない場合は合格

## 例

### 悪い例（いきなり実装 plan）

```markdown
## 実装方針

Redis を使う。以下のファイルを変更する。

- src/cache.ts（新規）
- src/config.ts
```

背景・成立条件・採否理由が無い。

### 良い例（方法論フェーズ）

```markdown
## 背景・制約

- セッション共有が必要。単一 AZ のみ。月次コスト上限あり。

## 現状調査

- 現状は in-memory。水平スケール時にセッションが分断される。

## 方法論・成立条件・限界

- 候補 A: Redis / 候補 B: sticky session
- 成立条件: 2 インスタンス以上で同一ユーザーがログイン維持できること
- 限界: Redis 障害時は全セッション喪失（DR 別途）

## スコープ外（本 plan）

- 実装 plan、変更ファイル一覧、CI 検証は **次フェーズ**。本 plan は方針合意まで。
```

## 補足

- 方法論フェーズでは `files-are-identified.md`、実装向け `must-have-verification-steps.md`、**`must-have-acceptance-criteria.md`** は **適用外**。未記載を重大にしない。方針合意の完了条件は本ルール（調査・方法論・記録）で確認する。
- plan file を書かず調査メモのみ返す場合もある（`draft` で方針節だけ出力）。その場合も実装スコープ外を明示する。
- 実装 plan フェーズへ移る条件: ユーザーが方針を **明示承認** した、または最初から実装依頼である。
