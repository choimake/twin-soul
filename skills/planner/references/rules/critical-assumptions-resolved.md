# クリティカル前提が Plan 段階で解消されているか

## ねらい

「実装時に実機検証」「後で確認」と書いて先送りした前提が、Plan 承認後に業務フローを崩すと手戻りが大きい。Plan 段階でクリティカル前提を解消するか、Plan 前の調査（Phase 0）として組み込む。

## クリティカル前提の定義

次のいずれかに該当する未確認事項:

- 成立しないと要件自体を満たせない（例: 外部 API が必要な操作をサポートしているか未確認）
- 設計の分岐（採用 / 不採用）がこの前提に依存している
- 実機・本番相当環境での確認が無いと見積もりやスコープが変わる

**軽微未確認**（実装の詳細調整で吸収可能なもの）は Plan に残してよい。例: エラーメッセージの文言、ログレベル、定数の微調整。

## チェック観点

- 「実装時に実機検証」「デプロイ後に確認」等で **クリティカル前提** が先送りされていないか
- 実機検証が必要と判明している場合、**Phase 0（Plan 前調査）** として plan に含まれているか
- 未解消のクリティカル前提が残る場合、リスクと対策で明示され、Plan 承認前にユーザー合意が取れる記述があるか
- 公式 docs・既存実装 Read・ユーザー確認で確定できる前提は、Plan に先送りせず記載されているか
- 動くか・見た目・API の未決を「実装時に確認」に残さず、plan 前に小さく試作しているか

## 指摘する基準

- クリティカル前提が「実装時に実機検証」等で先送りされている場合は **重大**
- 動くか・見た目・API の未決が「実装時に確認」のまま残っている場合は **重大**
- 実機検証が必要なのに Phase 0 が無く、いきなり実装 Phase から始まっている場合は **重大**
- 軽微未確認をリスク節に明記している場合は合格
- 調査完了まで Plan を書かない場合、Phase 0 の成果が **issue URL / ファイル `@path` / 調査メモへのリンク** で参照可能であること

## 例

### 悪い例

```markdown
## 実装方針

Phase 1: Webhook エンドポイントを実装する。

## リスクと対策

- 実装時に Fivetran から即時 ping が来るか実機で確認する
```

Webhook 登録の成否が前提に直結しているのに先送りしている。

### 良い例

```markdown
## Phase 0: 前提確認（Plan 承認前）

- [ ] 検証環境で Webhook 登録リクエストを送り、コールドスタート内に 200 が返ることを確認
- 根拠: 公式 docs [Cloud Run ...](https://...) — 登録時に同期 ping あり

## Phase 1: 実装

（Phase 0 合格後に着手）

## スコープ外

- Phase 0 未完了のまま Phase 1 へ進まない
```

## 補足

- 方法論のみの plan でも、採用方針の成立条件がクリティカル前提に該当する場合は同様に適用する。
- Plan エージェントや他者の主張は、critical files を Read して裏取りしてから Plan に採用する。
- 動くか・見た目・API は plan を書く前に小さく試作する。試作の手順書は本 skill に置かない。
