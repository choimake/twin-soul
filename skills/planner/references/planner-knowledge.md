# Planner 判断知識

この資料は `planner` skill の判断知識をまとめたものである。`SKILL.md` は使い方に留め、plan 生成・レビューの詳細判断はこの資料とテンプレートを起点にする。

テンプレート:

- [../assets/plan-template.md](../assets/plan-template.md)
- [../assets/review-output-template.md](../assets/review-output-template.md)

## この skill の役割

- plan file の品質を保証し、必須項目の漏れを防ぐ
- AI 自動レビューで plan file の完成度を高める
- Web 検索でベストプラクティスを取得し、plan に組み込む
- 実装フェーズでの手戻りを減らすため、受け入れ条件・検証手順を明確にする

## 呼び出し側が渡せる入力

- 対象 plan file の `@path`（既存 plan のレビュー時）
- タスク説明文（新規 plan 作成時）
- Web 検索キーワード（明示されていれば優先、無ければタスク内容から抽出）
- 保存先パス（`write-file` 時。未指定ならユーザーに確認する）
- 出力モード（`review` / `draft` / `write-file`）

未指定なら、この skill が会話から妥当な既定値を判断する。必要最低限の確認だけを追加する。

## 対象と探索の絞り方

1. 既存 plan file の `@path` が指定されていれば、それを対象にする。
2. 新規 plan 作成の依頼なら、タスク説明文を起点にする。
3. 出力モードが明示されていれば、それを優先する。未指定なら、既存 plan file がある場合は `review`、無ければ `draft` を既定にする。
4. `write-file` で保存先が明示されていない場合は、本文生成前に保存先パスを確認する。
5. Web 検索キーワードが明示されていれば優先し、無ければタスク内容から技術キーワード（言語、フレームワーク、パターン名）を抽出する。

## 相談・方法論整理と実装 plan の分離

依頼が次に該当する場合は **方法論フェーズ** として扱う（実装 plan は書かない）:

- 「どうやる？」「どっちがいい？」「方針どう思う？」「方法論を考えたい」
- 手段比較の前に Why・背景・制約が未整理

### 方法論フェーズの手順

1. **Why・背景・制約を先に確認**する。不足なら質問してから本文を書く。
2. 成果物は次の流れ: **(1) 現状調査 → (2) 方法論・成立条件・限界・前提 → (3) 記録**
3. 記録先は issue コメント、DR ドラフト、plan の「調査・方針」節のいずれか。plan file 全体を書かなくてよい。
4. 本文で **実装 plan・変更ファイル一覧・実装向け CI 検証はスコープ外** と明示する。
5. 実装は「次フェーズで planner / 実装者が扱う」と分離する。
6. 方針合意・承認待ちは本文の未決事項に置く。承認・採否をエージェントが完了にできる作業項目にしない。
7. 試用や判定の成功条件を書くなら、この会話内で不合格になり得る観測を書く。前後比較には比較前の実測を先行させる。絶対閾値は対象外。

plan file を書かず **調査メモのみ** 返す場合もある（`draft` で方針節だけ出力）。その場合も上記 4〜7 を守る。

### 実装 plan フェーズ

方法論が **ユーザー明示承認済み**、または最初から実装依頼の場合のみ [../assets/plan-template.md](../assets/plan-template.md) を使う。

## Plan生成の進め方（実装 plan）

1. タスク説明文から、背景、目的、スコープを抽出する。
2. Web 検索でベストプラクティスを取得する（最大 3〜5 件）。検索クエリはタスク内容 + "best practices" + 技術キーワード。
3. [../assets/plan-template.md](../assets/plan-template.md) を起点に、必須セクションを埋める。
4. 受け入れ条件は具体的かつ検証可能な形式で記述する（チェックボックス形式）。
5. ベストプラクティスセクションに Web 検索結果を統合する（URL とタイトル付き）。
6. 実装方針の冒頭に「基本方針: 時間は十分あるため、品質を最優先する」を必ず含める。**Phase 0**（Plan 前調査・クリティカル前提の解消）が必要なら Phase 1 より前に置く。実機検証が必要な場合は「実装時にやる」ではなく Phase 0 に組み込む。
7. 変更対象ファイルは「新規作成」と「既存ファイル更新」に分けて列挙する。
8. 検証セクションには、コマンド例と期待結果と、実行時の不合格観測を含める。前後比較を書くなら比較前の実測を Phase 0 に置く。

## レビュールールの適用順序

`references/rules/` 配下のルールをファイル名順で適用する：

1. `critical-assumptions-resolved.md` - クリティカル前提が Plan 段階で解消されているか
2. `files-are-identified.md` - 変更対象ファイルが特定されているか（方法論のみ plan では適用外）
3. `methodology-before-implementation.md` - 方法論相談と実装 plan が分離されているか
4. `must-have-acceptance-criteria.md` - 受け入れ条件が明確に定義されているか（方法論フェーズでは適用外。`methodology-before-implementation.md` で方針合意を確認）
5. `must-have-verification-steps.md` - 検証手順が具体的か（方法論のみ plan では実装検証は適用外）
6. `must-reference-best-practices.md` - ベストプラクティスと、採否が変わる数値・上限・契約の公式根拠を参照しているか
7. `scope-is-clear.md` - スコープが明確か

各ルールは個別に評価し、違反があれば優先度（重大 / 提案 / 任意）付きで指摘する。

## 優先度の基準

### `重大`

- 受け入れ条件が無い、または曖昧すぎる（実装 plan の場合）
- 検証手順が無い、または実行時の不合格観測が無い（実装 plan の場合）
- スコープが不明確で、何を作るのか分からない
- 変更対象ファイルが全く特定されていない（実装 plan の場合）
- クリティカル前提が「実装時に実機検証」等で先送りされている
- 相談系なのに Why・背景・制約が無く手段比較だけが書かれている
- 方法論 plan が承認・採否を作業項目にしている
- 採否・スコープ・見積もりが変わる断定に公式 URL・確認日・本文の一句が無い

### `提案`

- ベストプラクティスの参照が無い、または不十分
- リスクと対策セクションが無い
- 実装方針が大雑把すぎる

### `任意`

- 参照元セクションが無い
- フォーマットの統一（見出しレベル、リスト形式）

迷う場合は `提案` を既定にする。

## Web検索統合のロジック

1. タスク説明文から技術キーワードを抽出する（例: "React", "API", "TypeScript", "authentication"）。
2. 検索クエリは「技術キーワード + best practices + 2026」の形式にする。
3. 検索結果から信頼性の高いソース（公式ドキュメント、Thoughtbot、Atlassian、Martin Fowler、Anthropic など）を優先する。
4. 最大 3〜5 件に絞り、ベストプラクティスセクションに統合する。
5. 各ベストプラクティスはリンク形式で記述する（例: `[Title - Source](URL): 説明`）。
6. 採否・スコープ・見積もりが変わる断定は、採用 URL を WebFetch し、確認日と本文の一句を残してから書く。WebSearch のスニペットだけでは断定しない。取得失敗ならその旨を書いて提案指摘にする。

検索が失敗した場合や無関係な結果しか無い場合は、ユーザー指定キーワードでのフォールバック、または「ベストプラクティスの参照が不十分」として提案指摘を出す。

## 出力モードごとの期待

### `review`

- plan file を読み取り、`references/rules/` のルールを適用する
- レビュー結果を [../assets/review-output-template.md](../assets/review-output-template.md) の形式で返す
- 重大指摘があれば修正を促し、無ければ「レビュー合格」を明示する

### `draft`

- タスク説明文を起点に、plan file の下書き、または方法論フェーズの調査・方針メモを作成する
- Web 検索でベストプラクティスを取得し、統合する
- 下書き完成後、自動的に `review` モードを実行し、品質チェック結果を添える
- 重大指摘があれば、下書きを修正して再レビューする

### `write-file`

- `draft` と同じ手順で plan file、または方法論フェーズの調査メモを生成する
- 方法論フェーズの場合は plan テンプレ全体ではなく、背景・制約 / 現状調査 / 方法論・成立条件・限界 / スコープ外 / 未決事項 の節で保存する
- 保存先が明示されていれば、そのパスに保存する
- 保存先未指定なら、本文生成前にユーザーへ保存先パスを確認する
- 保存後、保存先パスとレビュー結果を報告する

## 応答時の明示事項

対象が未指定のとき:

- まず用途（新規 plan 作成 / 既存 plan レビュー / plan file 書き込み）を確認する短い質問だけを返す
- 使い方の例を簡潔に示す:
  - `/planner タスク説明` - 新規 plan の下書きを作成
  - `/planner review @path` - 既存 plan をレビュー
  - `/planner write-file <保存先パス> タスク説明` - plan を作成して指定パスに保存
- plan 保管ディレクトリ全体を見に行く前提の説明や、具体的な plan 案は出さない

対象が決まったら:

- Web 検索を実行する場合は、検索クエリを明示する
- レビュー結果は findings first を維持し、概要は必要最小限に留める
- 重大指摘があれば、修正案を添える
- レビュー合格なら、「ユーザー承認を求める」と明示する

## `scripts/`

追加しない（手順はテキストと WebSearch で足りる。同じ整形・検証を繰り返し自動化したくなったら `scripts/` を足す）。
