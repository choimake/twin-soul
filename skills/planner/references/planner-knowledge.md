# Planner 判断知識

この資料は `planner` skill の判断知識をまとめたものである。`SKILL.md` は使い方に留め、plan生成・レビューの詳細判断はこの資料とテンプレートを起点にする。

テンプレート:

- [../assets/plan-template.md](../assets/plan-template.md)
- [../assets/review-output-template.md](../assets/review-output-template.md)

## この skill の役割

- plan fileの品質を保証し、必須項目の漏れを防ぐ
- AI自動レビューで plan fileの完成度を高める
- Web検索でベストプラクティスを取得し、planに組み込む
- 実装フェーズでの手戻りを減らすため、受け入れ条件・検証手順を明確にする

## 呼び出し側が渡せる入力

- 対象plan fileの `@path`（既存planのレビュー時）
- タスク説明文（新規plan作成時）
- Web検索キーワード（明示されていれば優先、無ければタスク内容から抽出）
- 保存先パス（`write-file` 時。未指定ならユーザーに確認する）
- 出力モード（`review` / `draft` / `write-file`）

未指定なら、この skill が会話から妥当な既定値を判断する。必要最低限の確認だけを追加で行う。

## 対象と探索の絞り方

1. 既存plan fileの `@path` が指定されていれば、それを対象にする。
2. 新規plan作成の依頼なら、タスク説明文を起点にする。
3. 出力モードが明示されていれば、それを優先する。未指定なら、既存plan fileがある場合は `review`、無ければ `draft` を既定にする。
4. `write-file` で保存先が明示されていない場合は、本文生成前に保存先パスを確認する。
5. Web検索キーワードが明示されていれば優先し、無ければタスク内容から技術キーワード（言語、フレームワーク、パターン名）を抽出する。

## Plan生成の進め方

1. タスク説明文から、背景、目的、スコープを抽出する。
2. Web検索でベストプラクティスを取得する（最大3-5件）。検索クエリはタスク内容 + "best practices" + 技術キーワード。
3. [../assets/plan-template.md](../assets/plan-template.md) を起点に、必須セクションを埋める。
4. 受け入れ条件は具体的かつ検証可能な形式で記述する（チェックボックス形式）。
5. ベストプラクティスセクションにWeb検索結果を統合する（URLとタイトル付き）。
6. 実装方針の冒頭に「基本方針: 時間は十分あるため、品質を最優先する」を必ず含める。Phase 0, Phase 1, ... のような段階的なステップに分ける。
7. 変更対象ファイルは「新規作成」と「既存ファイル更新」に分けて列挙する。
8. 検証セクションには、コマンド例と期待結果を含める。

## レビュールールの適用順序

`references/rules/` 配下のルールをファイル名順で適用する：

1. `files-are-identified.md` - 変更対象ファイルが特定されているか
2. `must-have-acceptance-criteria.md` - 受け入れ条件が明確に定義されているか
3. `must-have-verification-steps.md` - 検証手順が具体的か
4. `must-reference-best-practices.md` - ベストプラクティスを参照しているか
5. `scope-is-clear.md` - スコープが明確か

各ルールは個別に評価し、違反があれば 優先度（重大 / 提案 / 任意）付きで指摘する。

## 優先度の基準

### `重大`

- 受け入れ条件が無い、または曖昧すぎる
- 検証手順が無い、または「確認する」だけで具体性が無い
- スコープが不明確で、何を作るのか分からない
- 変更対象ファイルが全く特定されていない

### `提案`

- ベストプラクティスの参照が無い、または不十分
- リスクと対策セクションが無い
- 実装方針が大雑把すぎる

### `任意`

- 参照元セクションが無い
- フォーマットの統一（見出しレベル、リスト形式）

迷う場合は `提案` を既定にする。

## Web検索統合のロジック

1. タスク説明文から技術キーワードを抽出する（例: "React", "API", "TypeScript", "authentication"）。
2. 検索クエリは「技術キーワード + best practices + 2026」の形式にする。
3. 検索結果から信頼性の高いソース（公式ドキュメント、Thoughtbot、Atlassian、Martin Fowler、Anthropicなど）を優先する。
4. 最大3-5件に絞り、ベストプラクティスセクションに統合する。
5. 各ベストプラクティスはリンク形式で記述する（例: `[Title - Source](URL): 説明`）。

検索が失敗した場合や無関係な結果しか無い場合は、ユーザー指定キーワードでのフォールバック、または「ベストプラクティスの参照が不十分」として 提案指摘を出す。

## 出力モードごとの期待

### `review`

- plan fileを読み取り、`references/rules/` のルールを適用する
- レビュー結果を [../assets/review-output-template.md](../assets/review-output-template.md) の形式で返す
- 重大指摘があれば修正を促し、無ければ「レビュー合格」を明示する

### `draft`

- タスク説明文を起点に、plan fileの下書きを作成する
- Web検索でベストプラクティスを取得し、統合する
- 下書き完成後、自動的に `review` モードを実行し、品質チェック結果を添える
- 重大指摘があれば、下書きを修正して再レビューする

### `write-file`

- `draft` と同じ手順でplan fileを生成する
- 保存先が明示されていれば、そのパスに保存する
- 保存先未指定なら、本文生成前にユーザーへ保存先パスを確認する
- 保存後、保存先パスとレビュー結果を報告する

## 応答時の明示事項

対象が未指定のとき:

- まず用途（新規plan作成 / 既存planレビュー / plan file書き込み）を確認する短い質問だけを返す
- 使い方の例を簡潔に示す:
  - `/planner タスク説明` - 新規planの下書きを作成
  - `/planner review @path` - 既存planをレビュー
  - `/planner write-file <保存先パス> タスク説明` - planを作成して指定パスに保存
- plan保管ディレクトリ全体を見に行く前提の説明や、具体的なplan案は出さない

対象が決まったら:

- Web検索を実行する場合は、検索クエリを明示する
- レビュー結果は findings first を維持し、概要は必要最小限に留める
- 重大指摘があれば、修正案を添える
- レビュー合格なら、「ユーザー承認を求めます」と明示する

## `scripts/`

追加しない（手順はテキストと WebSearch で足りる。同じ整形・検証を繰り返し自動化したくなったら `scripts/` を足す）。
