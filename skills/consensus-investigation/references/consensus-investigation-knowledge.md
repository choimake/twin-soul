# consensus-investigation 判断知識

この資料は `consensus-investigation` skill の判断知識をまとめたものである。`SKILL.md` は使い方に留め、適用判定・独立性・突合・確度の定義・エージェント数の詳細判断はこの資料を起点にする。

テンプレート:

- [../assets/consensus-report-template.md](../assets/consensus-report-template.md)
- [../config/defaults.yaml](../config/defaults.yaml)

読み方:

- 着手前は「適用判定」「設定の解決」「対象 skill の渡し方」を優先する
- 委譲時は「独立性の担保」「調査委譲に含める項目」を優先する
- 集計時は「突合基準」「判定投票型の集計」「確度の定義と限界」を優先する

## 用語

- **メインエージェント**: 調査を委譲し、突合・確度付け・報告だけするオーケストレーター本体
- **調査サブエージェント**: 同一の調査を独立に実行する委譲先エージェント
- **出現数**: 同一とみなした指摘を報告した調査サブエージェントの数（k/N と表記）
- **確度**: 出現数から機械的に決まる 3 段階のラベル（高・中・低）。再現性の指標であり、正しさの保証ではない
- **指摘列挙型**: 自由記述の指摘リストを返す調査（例: コードレビュー）
- **判定投票型**: 固定の項目リストへ判定を返す調査（例: gap-analysis の可 / 条件付き可 / 不可）

以降、本文はこの用語で統一する。

## 適用判定

本 skill は調査系タスク専用とする。判定基準は成果物の種類で機械的に決める。

- **適用する**: 成果物が指摘・判定・情報であり、対象を変更しないタスク。例: コードレビュー、gap 分析、原因調査、仕様調査、ドキュメントレビュー
- **適用しない**: 成果物が対象の変更そのものであるタスク。例: 実装、バグ修正、リファクタリング、ドキュメント作成・改稿、設定変更

適用しない場合の対応:

- 本 skill を開始せず、調査系タスク専用である旨を短く伝える
- 実装×独立レビューのループが目的なら `verification-loop` を案内する
- 「合議で」「確度付きで」の語があっても、成果物が変更ならこの判定を優先する
- 変更タスクの前段の調査だけを切り出せるなら、その調査部分に限って適用してよい（変更は本 skill の外でする）

## 設定の解決

優先順位（上ほど強い）:

1. 呼び出し引数（タスク本文・直前指示に含まれる指定）
2. [../config/defaults.yaml](../config/defaults.yaml)
3. なお未確定なら着手前にユーザーへ確認する

解決する項目:

- `agent_count`（未指定時の既定は 3）
- `investigator_model`（空なら実行環境の既定モデルに従う）
- 調査対象・スコープ
- 対象 skill（併用指定があれば SKILL.md のパス）

### モデル指定

- モデル識別子は実行環境の委譲ツール（例: Task / Agent）が受け付ける文字列をそのまま使う
- Cursor と Claude Code など、ツールごとに識別子の形が違う。skill 側で製品固有の slug を決め打ちしない
- 特定モデルを渡す必要がある場合、親モデルを継承して `model` 指定が無効になる fork 経路は使わない
- 誤り相関を下げたい場合は、体ごとに別モデルを引数で指定してよい（「誤り相関と緩和策」を参照）

## 対象 skill の渡し方

- 併用指定された調査系 skill がある場合、その SKILL.md のファイルパスを委譲プロンプトに含め、「このファイルを読み、その手順に従って調査せよ」と指示する
- 対象 skill の手順にユーザー確認を求めるステップがあるなら、メインエージェントが委譲前に解決して確定値を渡す（調査サブエージェントはユーザーに確認できない）
- 対象 skill も調査系であることを適用判定で確認する。変更を伴う skill（例: verification-loop）は対象にしない
- 対象 skill がない素の調査依頼でも、本 skill は単体で使える

## 独立性の担保

出現数を確度として使えるのは、各体の調査が独立しているときだけである。

- 各調査サブエージェントには同一の委譲プロンプトを渡し、並列に起動する
- 他の調査サブエージェントの結果・途中経過を渡さない
- メインエージェントの仮説・予想・気になっている箇所を渡さない（誘導すると出現数が確度として機能しなくなる）
- 再実行や追加調査が必要になったら、毎回新しい調査サブエージェントを立てる

## 調査委譲に含める項目

必ず渡す:

- 調査の目的と対象範囲（ファイル・ディレクトリ・diff の特定方法）
- 対象 skill の SKILL.md パスと「読んで手順に従う」指示（併用時）
- 読み取り専用である旨（対象を変更しない）
- 返す形式（下記の構造化フォーマット）
- 確定した `investigator_model`（ツールが受け付ける形式）

指摘列挙型の返す形式は、突合できるように指摘ごとに次を強制する:

```text
- 位置: [ファイル:行、または対象の特定子]
- 分類: [correctness / security / performance / maintainability など調査に応じた分類]
- 重要度: [高 / 中 / 低]
- 主旨: [1〜2 文の指摘内容]
- 根拠: [該当箇所の引用または理由]
```

- 「重要な順に上位だけ」と絞らせず、見つけた指摘は全件返させる。体ごとに違う基準で絞ると出現数が歪む
- 判定投票型では、項目リストと判定の選択肢（例: 可 / 条件付き可 / 不可）、判定ごとの根拠を返す形式を渡す

## 突合基準（指摘列挙型）

1. 位置と分類でグルーピングする
2. 同一グループ内の主旨をメインエージェントが読み、意味的に同じ問題を指しているかで同一性を最終判定する
3. 行番号の多少のずれ、言い回しの違いは同一とみなしてよい。問題の原因や求める対処が異なるなら別の指摘として扱う
4. 同一とみなした指摘の主旨と根拠は、最も具体的な記述を代表として採用する
5. 重要度が体ごとに割れた場合は最頻値を採用し、割れたことを備考に残す

## 判定投票型の集計

- 項目ごとに判定の分布を数える（例: 可 2 / 条件付き可 1）
- 全員一致 = 高確度、過半一致 = 中確度（少数意見を併記する）、それ以外の割れ = 低確度とし「要確認」を明記する
- 判定が割れた項目は、各体の根拠の違いを要約して残す。割れの理由がスコープや前提の解釈差なら、前提を確定して再実行する価値がある

## 確度の定義と限界

| 確度 | 条件                 | 意味                                     |
| ---- | -------------------- | ---------------------------------------- |
| 高   | 出現数 = N（全員一致） | N 体すべてが独立に再現した               |
| 中   | 出現数 > N/2（過半）   | 過半が再現した                           |
| 低   | それ以外（単独を含む） | 再現性は低いが、価値ある指摘の可能性は残る |

限界を踏まえた扱い:

- 確度は「独立実行での再現性」であり「正しさの保証」ではない。同一モデルの複数実行は誤りも相関する（誤答時のモデル間一致率は約 6 割という報告がある）ため、全員一致の誤指摘があり得る
- 合意度によるふるい分けは見落とし（recall）の改善に効く一方、誤検知（precision）はあまり減らない。高確度でも採用前に根拠を確認する
- 単独指摘（低確度）は捨てない。網羅的な 1 体だけが見つけた真の指摘があり得る。低確度ラベル付きで必ず報告に残す
- 指摘の採否はユーザーが判断する。確度を理由にメインエージェントが指摘を除外しない

## 誤り相関と緩和策

同一モデル・同一プロンプトの N 体は誤りが相関し、独立仮定より確度の意味が弱くなる。緩和策は効果が高い順に:

1. **モデル多様化**: 体ごとに別モデルを引数で指定する。失敗源の直交性に最も効く
2. **サンプリングのゆらぎ**（温度など）: 同一モデル内の分散を注入するだけで、共通バイアスは解消しない。既定の挙動に任せてよい

観点分割（security 担当・performance 担当のような分担）は網羅性を上げる別の設計であり、体ごとに見るものが違うと出現数を確度として使えない。本 skill ではしない。

## エージェント数の目安

- 既定は 3。全員一致 = 高、2/3 = 中、単独 = 低が 3 段階に自然に対応し、二値の判定投票でも同数にならない
- 重要度の高い調査では 5 まで増やす価値がある。それ以上は収穫逓減が大きく、コストに見合わないことが多い
- 2 は過半と全員一致が区別できないため使わない。偶数は判定投票が割れ得るため避ける

## 参考

設計の裏付けにした主な知見:

- 同一コード変更への N 回独立レビュー＋集約は見落としを大きく減らすが、誤検知の削減効果は小さい: Multi-Review（arXiv:2509.01494）
- 全員一致 / 過半数 / 単独の 3 層 confidence と「単独指摘に価値ある洞察が残る」教訓: Mozilla.ai Star Chamber（<https://blog.mozilla.ai/the-star-chamber-multi-llm-consensus-for-code-quality/>）
- 同一モデルの誤りは強く相関する（誤答時一致率 ~60%）。モデル多様化が支配的な緩和要因: Correlated Errors in Large Language Models（arXiv:2506.07962）
- 自由記述への多数決には意味的な同値判定が必要: Universal Self-Consistency（arXiv:2311.17311）
- 多数決の利得は少数サンプルで飽和する（収穫逓減）: Self-Consistency（arXiv:2203.11171）とその後続報告
