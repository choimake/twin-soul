# consensus-investigation テストプロンプト

最初は 2〜3 件に絞る。

## セット確認

- Coverage: 併用型、素の調査型、適用判定（変更タスクの拒否）、対象外の単発レビュー、スライス並列、最良採用
- Trigger balance: should-trigger と should-not-trigger が混ざっているか
- Near miss: 「合議」の語を含む変更タスクが対象外になっているか
- Diversity check: 同じ言い回しだけを変えた prompt 群になっていないか
- Realism check: 実際のユーザーが言いそうな背景と対象があるか
- 過適合リスク: このセットにだけ最適化しても意味がない箇所はどこか

## プロンプト 1

- Type: 調査系 skill との併用指定（指摘列挙型）
- Should trigger: true
- 目的: 対象 skill の SKILL.md パスを依頼に含め、N 体並列→突合→確度順レポートまで進むか
- 理由: 本 skill の主用途。既存 skill を無改変のまま強化できることの確認
- Prompt:

```text
universal-code-reviewer の観点で scripts/ をレビューしてほしい。
1回だと結果がぶれるので、合議で確度付きにして。
```

- Success signals:
  - 着手前に対象・対象 skill・エージェント数・モデルを提示する
  - 同一の依頼文で複数の調査サブエージェントを並列起動し、互いの結果を渡さない
  - 統合レポートが確度順で、単独指摘も低確度として残る
- 過適合リスク: universal-code-reviewer 以外の調査系 skill でも同じ渡し方になること

## プロンプト 2

- Type: 素の調査依頼（skill 名なし）
- Should trigger: true
- 目的: 対象 skill なしでも単体で合議調査に入るか。undertrigger を避けられているか
- 理由: skill 名を知らないユーザーの依頼でも trigger できるかの確認
- Prompt:

```text
この障害の原因になり得る箇所を調べてほしい。見落としが怖いので、
複数のエージェントに独立で調べさせて、意見が一致したものから順に教えて。
```

- Success signals:
  - 適用判定を通過し（調査系タスク）、調査対象・スコープの確認に進む
  - 出現数に基づく確度（高・中・低）で統合報告する
  - メインエージェントが自分で調査を始めない
- 過適合リスク: 「障害調査」という題材の文言に過適合しないこと

## プロンプト 3

- Type: 「合議」の語を含む変更タスク（対象外）
- Should trigger: false
- 目的: 適用判定で変更タスクを拒否し、代替を案内できるか
- 理由: trigger 語だけで発動しない境界の確認。ユーザー要望「調査系タスク以外では機能しない」の中核
- Prompt:

```text
このリファクタリングを合議でやってほしい。複数エージェントで実装して、一番いい実装を採用して。
```

- Success signals:
  - 合議調査を開始せず、調査系タスク（成果物が指摘・判定・情報）専用である旨を伝える
  - 実装×独立レビューのループが目的なら verification-loop を案内する
  - 調査サブエージェントに変更をさせない
- 過適合リスク: 「リファクタリング」の語だけで拒否せず、成果物が変更かどうかで判定すること

## プロンプト 4

- Type: 通常の単発レビュー（対象外）
- Should trigger: false
- 目的: 合議の指定がない単発レビューを本 skill に引き寄せないこと
- 理由: description の境界確認。既定でコストを N 倍にしない
- Prompt:

```text
この PR の差分をレビューして。改善点ある？
```

- Success signals:
  - 合議調査を開始しない
  - 通常のコードレビュー skill や通常レビュー手順へ寄せる
- 過適合リスク: 「レビュー」の語だけで常に拒否しないこと（合議・確度付きの明示時は trigger する）

## プロンプト 5（任意・判定投票型）

- Type: gap-analysis との併用（判定投票型）
- Should trigger: true
- 目的: 固定項目への判定を項目単位の投票として集計し、割れた項目を「要確認」にできるか
- 理由: 指摘列挙型と集計方法が異なる分岐の確認
- Prompt:

```text
gap-analysis の手順で、この PRD の要件が今の実装で満たせるか判定してほしい。
判定は3人に独立でやらせて、意見が割れた要件を教えて。
```

- Success signals:
  - 項目ごとに判定の分布（例: 可 2 / 条件付き可 1）を集計する
  - 割れた項目を低確度・要確認として、割れた理由の要約付きで報告する
- 過適合リスク: gap-analysis 固有の判定凡例に過適合せず、他の判定型調査でも同じ集計になること

## プロンプト 6

- Type: スライス並列（合議手順を回さない）
- Should trigger: false
- 目的: 範囲を分けて並列に調べる依頼を、出現数確度の合議にしないこと
- 理由: 見るものが違うと出現数は再現性にならない
- Prompt:

```text
src/ と tests/ と scripts/ を分けて、並列にレビューして。
全部終わったら一つの報告にまとめて。
```

- Success signals:
  - 合議の手順（同一依頼×N、出現数確度）を開始しない
  - 合議ではない旨を伝え、通常の並列調査として扱う
  - 出現数の高・中・低を付けない
- 過適合リスク: ディレクトリ名の列挙だけで拒否せず、「範囲を分けて調べる」かどうかで判定すること

## プロンプト 7

- Type: 最良採用（対象外）
- Should trigger: false
- 目的: 複数案から一番いいものを取る依頼を合議にしないこと
- 理由: 合議は再現性であり、最良採用とは別物
- Prompt:

```text
この障害の調べ方をいくつか出して、一番筋がいい調査方針を採用して進めて。
```

- Success signals:
  - 合議調査を開始しない
  - 本 skill の対象外である旨を伝える
  - 出現数確度を付けない
- 過適合リスク: 「いくつか」の語だけで拒否せず、最良を取る意図かどうかで判定すること
