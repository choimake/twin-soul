# Use Case Description 判断知識

この資料は `use-case-description` skill の判断知識をまとめたものである。`SKILL.md` は使い方に留め、ユースケース記述の生成・レビューの詳細判断はこの資料とテンプレートを起点にする。

テンプレート:

- [../assets/use-case-template.md](../assets/use-case-template.md)
- [../assets/review-output-template.md](../assets/review-output-template.md)

## この skill の役割

- ユースケース記述 Markdown の構造品質を保証し、必須項目（アクター、事前・事後条件、番号付きフロー、暗黙の前提、用語集）の漏れを防ぐ
- ルールベースのレビューで完成度を高める
- **他 skill やリポジトリ内の特定パスに依存せず**、下記の対象範囲だけを本資料とテンプレートで定義する

## 本 skill の対象範囲

本 skill が扱うのは **ユースケース記述（use case description）の Markdown** のみである。次のような文書・成果物は対象外とする（どのツール・skill で書くかは本 skill は規定しない）。

- ユースケース図（UML 図の作図）
- 要求定義文書全体の章立て・層の整理
- PBI・受入基準・ユーザーストーリー自体の起案
- 実装手順・変更ファイル一覧を主体とする計画書

位置づけは「ステークホルダー要求（利用シナリオ）→ **ユースケース記述** → 機能要求 / PBI 受入基準」の橋渡し層である。入力はユーザーストーリー等の上流文書、出力の各フローは機能要求や受入基準へ展開される入力になる。

## 呼び出し側が渡せる入力

- 対象ユースケース記述の `@path`（レビュー時）
- 入力となるユーザーストーリー・利用シナリオ（新規下書き時。`@path` または本文貼り付け）
- 対応ストーリー ID（トレーサビリティ用）
- 保存先パス（未指定ならユーザーに確認する。既定ディレクトリは設けない）
- 出力モード（`review` / `draft` / `write-file`）

未指定なら会話から妥当な既定値を判断する。必要最低限の確認だけ追加する。**入力ストーリーに書かれていない事実を当て推量で埋めない**。成立に必要なら「暗黙の前提」として明示し、確信が持てなければユーザーに確認する。

## 書式の選択（fully dressed / 簡略版）

記述の詳細度は用途で選ぶ（Cockburn の brief / casual / fully dressed に対応）。

- **fully dressed（既定）**: テンプレート全項目。実装・テストの入力になる重要・複雑なユースケースに使う
- **簡略版**: ユースケース名・主アクター・事前条件・事後条件（成功時）・基本フロー・主要な分岐だけに絞る。初期検討や単純な機能で、ユーザーが軽量を求めたときに使う

迷う場合は fully dressed を既定にする。

## 各項目の書き方

- ユースケース名: 主アクターのゴールを動詞句で書く（例:「〜を設定する」「〜を閲覧する」）
- ゴールの粒度: ユーザー目標レベルに揃える。「一人・一箇所・一度に」完了し、基本フローが 3〜9 ステップに収まるのが目安。超えるなら分割か下位機能への切り出しを検討する
- アクター: 文書冒頭に表で定義し、各ユースケースでは主アクター（ゴールを開始する者）と副アクターを区別する
- 事前条件: 開始前に**真と保証される**条件として書く。フロー中で事前条件を検査するステップは書かない（検査が必要ならそれは事前条件ではなく、フロー内の判定と例外フローにする）
- トリガー: 開始の契機。事前条件（状態）と区別する
- 事後条件（成功時）: 正常完了時に真である状態（成功時保証）
- 事後条件（失敗時）: 失敗・異常終了でも守られる状態（最低保証）。「何も保存されず、既存の状態が維持される」のような形で書く
- 基本フロー: アクターとシステムを主語にした番号付きステップ。最頻かつゴールに到達する経路だけを書き、分岐を混ぜない
- 代替フロー: 基本フローのステップ番号に `〈N〉a` / `〈N〉a-1` 形式で紐づける。**事後条件（成功時）に到達する**別経路に使い、復帰先（基本フロー N に戻る／成功として終了）を必ず書く
- 例外フロー: E 番号を振り、**事後条件（成功時）に到達せず終了する**（または復帰する）経路に使う。発生ステップは「原因が生じた瞬間」ではなく「**検出されるステップ**」を書き、応答と終了・復帰の仕方を明示する
- 用語集: 本文で使った用語・英語・定義を表で揃える。本文の語と用語集の語を一致させる

任意で足してよい項目（既定では省く）: スコープ（対象システムの範囲）、ゴールレベル、利害関係者と関心事、任意ステップで起こる例外の `*a` 表記、技術・データのバリエーション。複数チーム・複数システムにまたがるときに検討する。

## 暗黙の前提の扱い

入力ストーリーには書かれていないが、フローの成立に必要な仮定は「暗黙の前提」として文書冒頭に A 番号（A1〜）で列挙し、依存する箇所から（A1）の形で参照する。前提の妥当性はユーザーが判断できるよう、置いた解釈を隠さない。前提が増えすぎる（目安: 7 個超）なら、入力ストーリー側の不足としてユーザーに確認する。

## レビュールールの適用順序

`references/rules/` 配下を **ファイル名の辞書順** で適用する。

1. `must-distinguish-alternative-exception.md`
2. `must-flow-numbering.md`
3. `must-guarantee-style-conditions.md`
4. `should-explicit-assumptions.md`
5. `should-glossary-and-traceability.md`

各ルールは個別に評価し、違反があれば 優先度（重大 / 提案 / 任意）付きで指摘する。

## 優先度の基準

### 重大

- 代替フローと例外フローの区別が事後条件と矛盾している（ゴール未達の経路が代替に置かれている等）
- フローの番号付けが基本フローのステップに紐づいていない、または復帰先・終了が読み取れない
- 事前条件・事後条件が無い、またはフロー中で事前条件を再検査している

### 提案

- ストーリーに無い前提に依存しているのに、暗黙の前提として明示されていない
- 用語集が無い、または本文の用語と食い違う
- 対応ストーリーへの紐づけが無い

### 任意

- 基本フローが 3〜9 ステップの目安から外れる（分割の検討余地）
- 表形式・見出しレベルの揺れ

迷う場合は `提案` を既定にする。

## 出力モードごとの期待

### `review`

- 対象を読み取り、`references/rules/` を適用する
- [../assets/review-output-template.md](../assets/review-output-template.md) の形式で返す
- 重大 があれば修正を促し、無ければレビュー合格を明示する

### `draft`

- 入力ストーリーを起点に、[../assets/use-case-template.md](../assets/use-case-template.md) の枠でユースケース記述を作成する
- 章を省略しない。該当が無い章は「なし」と書くか、省いた理由を短く添える
- 採用した暗黙の前提（A 番号）を本文とは別に短く要約し、ユーザーが妥当性を判断できるようにする
- 完成後、自動的に `review` 相当のチェック結果を添える。重大 があれば下書きを修正して再チェックする

### `write-file`

- `draft` と同様に本文を生成する
- 保存先が明示されていればそのパスへ保存する。未指定なら、本文生成前にユーザーへ保存先ディレクトリ（またはフルパス）を確認する。ファイル名のみ未指定の場合は内容から生成する（例: `usecase.md`、`lp-routing-usecase.md`）
- 保存後、パスとレビュー結果を報告する

## 応答時の明示事項

対象が未指定のとき:

- 新規作成 / 既存レビュー / ファイル書き込みのどれかを短く確認する
- 新規作成で入力ストーリーが無いときは、ストーリー（またはゴールとアクター）の提示を求める

本 skill を実行するときは **他 skill を読みに行かない**。関連する別文書がある場合は、ユーザーが `@path` で渡す。

`scripts/` を本 skill に追加しない判断をした理由:

- テンプレートとルールだけで運用できるため。番号整合の機械検証等が繰り返し必要になった時点で改めて追加を検討する。

- [Alternative flow vs exception flow — ModernAnalyst](https://www.modernanalyst.com/Careers/InterviewQuestions/tabid/128/ID/804/What-is-the-difference-between-a-use-case-alternative-flow-and-an-exception-flow.aspx): 代替＝成功事後条件に到達、例外＝未達で終了、の判定基準
- [Use Case Preconditions and Triggers — Tyner Blain](https://tynerblain.com/blog/2007/03/08/use-case-preconditions-and-triggers/): 事前条件は保証として書き再検査しない。トリガーとの区別
- [Getting Started With Use Case Modeling — Oracle](https://www.oracle.com/technetwork/developer-tools/jdev/gettingstartedwithusecasemodeling-133857.pdf): 成功時保証と最低保証の書き分け
