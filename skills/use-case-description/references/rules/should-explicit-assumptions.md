# 暗黙の前提が明示され本文から参照されているか（ユースケース記述）

## ねらい

ユーザーストーリーに書かれていない仮定を無言で採用すると、記述の成立条件が読み手に見えず、前提が崩れたときに原因を追えない。採用した解釈を A 番号付きで明示し、依存箇所から参照できる状態にする。

## チェック観点

- ストーリーに無い事実にフローや条件が依存している場合、それが「暗黙の前提」として列挙されているか
- 各前提に番号（A1〜）が振られ、依存する箇所から（A1）の形で参照されているか
- 前提が「成立に必要な解釈」になっているか（設計判断や実装詳細を前提に紛れ込ませていないか）

## 指摘する基準

- ストーリーに無い前提に依存しているのに前提として書かれていない場合は **提案**
- 前提はあるが番号が無い、または本文から参照されていない場合は **提案**
- 前提の数が多すぎる（目安: 7 個超）場合は **任意**（入力ストーリー側の不足としてユーザー確認を促す）

## 例

### 悪い例

```markdown
### 基本フロー

2. 運用者は、遷移先として配信する LP を選択する。
```

（LP が事前に登録済みであるという、ストーリーに無い前提に無言で依存している）

### 良い例

```markdown
## 暗黙の前提

- A1. LP はバリアントを含めて事前にシステムへ登録されている。

## UC-01

| 事前条件 | ルーティング先とする LP が登録済みである（A1） |
```

## 補足

- 前提の明示は「当て推量で埋めない」の実現手段である。確信が持てない前提は、置く前にユーザーに確認する
