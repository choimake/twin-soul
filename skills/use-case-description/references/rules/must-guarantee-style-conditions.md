# 事前条件・事後条件が保証として書かれているか（ユースケース記述）

## ねらい

事前条件・事後条件はユースケースの「契約」であり、これが無いと成功・失敗それぞれの終了状態を検証できない。事前条件は開始前に真と保証される状態、事後条件は成功時・失敗時の両方の終了状態として書く。

## チェック観点

- 事前条件があり、「開始前に真と保証される状態」として書かれているか（操作手順や願望になっていないか）
- フロー中に事前条件を再検査するステップが無いか（検査が必要ならフロー内の判定＋例外フローにする）
- 事後条件（成功時）が、正常完了時に真である状態として書かれているか
- 事後条件（失敗時）が、失敗しても守られる状態（最低保証）として書かれているか
- トリガー（開始の契機）が事前条件（状態）と区別されているか

## 指摘する基準

- 事前条件または事後条件（成功時）が無い場合は **重大**
- フロー中で事前条件を再検査している場合は **重大**
- 事後条件（失敗時）が無い場合は **提案**（失敗経路が無いユースケースでは省略してよい）
- トリガーと事前条件が混在している場合は **提案**

## 例

### 悪い例

```markdown
| 事前条件 | 運用者がログインを試みる |

### 基本フロー

1. システムは、対象が登録済みであることを確認する。
```

（事前条件が状態でなく操作になっており、フロー冒頭で事前条件の再検査をしている）

### 良い例

```markdown
| 事前条件 | 対象の LP が登録済みである（A1） |
| 事後条件（成功時） | 設定が保存され、有効化されている |
| 事後条件（失敗時） | 設定は保存されず、既存の設定状態が維持される |
| トリガー | 運用者が設定の登録を開始する |
```

## 補足

- 事後条件（失敗時）＝最低保証は「何も壊れていないこと」の言明であり、例外フローの終了状態はこれと整合させる
