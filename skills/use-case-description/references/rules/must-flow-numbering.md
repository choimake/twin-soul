# フローの番号付けと復帰先が明確か（ユースケース記述）

## ねらい

分岐がどのステップから始まり、どこへ戻る（または終わる）かが書かれていないと、経路の全体像を再構成できず、抜け漏れの検出もできない。番号規約で分岐点と復帰先を機械的に追える状態にする。

## チェック観点

- 基本フローが番号付きステップで、アクターまたはシステムを主語に書かれているか
- 代替フローが基本フローのステップ番号に紐づいているか（`3a`、`3a-1` のような形式）
- 代替フローの各経路に復帰先（基本フロー N に戻る／成功として終了）が書かれているか
- 例外フローに識別番号（E1〜）と発生ステップがあるか
- 発生ステップが「原因が生じた瞬間」ではなく「**検出されるステップ**」で書かれているか
- 参照先のステップ番号が実在するか（基本フローの改番後のずれが無いか）

## 指摘する基準

- 代替フローが基本フローのステップに紐づいていない、または復帰先が無い場合は **重大**
- 例外フローに発生ステップが無い、または終了・復帰の仕方が読み取れない場合は **重大**
- 参照先のステップ番号が実在しない場合は **重大**
- 発生ステップが検出ステップでなく原因発生時点で書かれている場合は **提案**

## 例

### 悪い例

```markdown
### 代替フロー

- 複数バリアントを設定する場合は、複数指定できる。
```

（どのステップの分岐か、どこへ戻るかが不明）

### 良い例

```markdown
### 基本フロー

1. 運用者は、対象を指定する。
2. 運用者は、設定内容を保存する。
3. システムは、設定を保存し、有効化する。

### 代替フロー

- **1a. 対象を一覧から選ぶ場合**
  - 1a-1. 運用者は、一覧から対象を選択する。
  - 1a-2. 基本フロー 2 に戻る。
```

## 補足

- 複数ステップにまたがって検出しうる例外は「発生ステップ: 基本フロー 2〜4」のように範囲で書き、どこで検出しても応答が同じであることを明記する
- 番号規約の出典: Cockburn の Extensions 記法（[Business Analyst Times — Use Case Goals, Scenarios and Flows](https://www.batimes.com/articles/use-case-goals-scenarios-and-flows/)）
