# 代替フローと例外フローが事後条件で区別されているか（ユースケース記述）

## ねらい

代替と例外の区別が曖昧だと、失敗時の振る舞い（何が保証され、どう終了するか）が読み手ごとにぶれ、実装・テストで手戻りが起きる。区別の基準を「どの事後条件に到達するか」に固定する。

- 代替フロー: 基本フローとは別経路だが、**事後条件（成功時）に到達する**
- 例外フロー: 事後条件（成功時）に**到達せず**、失敗時の保証（最低保証）を満たして終了する

## チェック観点

- 代替フローの各経路が、復帰または成功終了により事後条件（成功時）に到達するか
- 例外フローの各経路が、応答と終了（または復帰）の仕方を明示し、事後条件（失敗時）と整合するか
- ゴール未達で終了する経路が代替フローに紛れていないか（逆も）

## 指摘する基準

- ゴール未達で終了する経路が代替フローに置かれている、またはその逆の場合は **重大**
- 例外フローの終了時状態が事後条件（失敗時）と矛盾する場合は **重大**
- 経路がどちらに属すか本文から判別できない場合は **提案**

## 例

### 悪い例

```markdown
### 代替フロー

- **4a. 保存処理でシステム障害が発生した場合**
  - 4a-1. システムは、エラーを表示する。
```

（ゴール未達で終了する経路が代替フローに置かれ、終了の仕方も書かれていない）

### 良い例

```markdown
### 代替フロー

- **3a. 複数バリアントを設定する場合**
  - 3a-1. 運用者は、配信するバリアントを複数指定する。
  - 3a-2. 基本フロー 4 に戻る。

### 例外フロー

- **E3. 保存処理で一時的なシステム障害が発生した**
  - 発生ステップ: 基本フロー 5
  - システムは、設定を保存せずエラーを提示する。ユースケースを終了する。再度の保存操作により成功しうる。
```

## 補足

- 一時的な障害（リトライで解消しうる）と恒久的な障害（解消しない）を分けて書くと、失敗時の期待動作がテスト可能になる
