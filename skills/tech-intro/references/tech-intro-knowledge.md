# 技術の入門教材 判断知識

`tech-intro` skill の判断知識である。手順は [../SKILL.md](../SKILL.md) にある。

## 読み手

読み手はソフトウェアエンジニアである。その技術の用語も仕組みも知らない。プログラミングや HTTP の入門はしない。長い文章から形を組み立てられるとは仮定しない。見て分かることを先に置き、文章は図の読み方に留める。

書く前に、次の四つを一文ずつ決める。誰が読むか。その人が何を知っていて、題材の分野の何を知らないか。何を伝えるか。読み終えて何をしてほしいか。

## 要点を絞る

情報が多いほど、要点はつかみにくくなる。入門の価値は、何を書かないかで決まる。

- 書く前に、読み終えて覚えていてほしいことを3〜5個に絞る。これを要点と呼ぶ。冒頭に `data-goals` の番号付きリストで見せる
- 一つ目は「何であるか」である。製品の用語を使わず、どの分野の、何を作るための、どんな種類のものかを言う。例:「アプリの中の長い処理を、途中で落ちても続きから動かすためのサービス」「ロボットのアプリケーションを作るための開発基盤」
- 残りは、動きの核心と、使う側が間違えやすいことから選ぶ
- 本文に入れるのは、要点のどれかに効く事実だけである。公式で確かめられたことでも、要点に効かなければ書かない。詳しく知りたい人には、公式ページへのリンクで足りる
- 第1部は要点を支える順に厚く書く。第2部は、使い始めるときに要る判断だけを短く書く
- 書いたあとで、どの要点にも効かない段落、図と同じことを言う段落、同じ判断の言い直しを削る

スクリプトが量を見る。要点は5個、章は12個、見出しは25字、各章の文章は600字、文章の合計は4000字、各章で定義する語は3語までである。図、コード、表、出典、クイズは文章に数えない。末尾の3章（チェックリスト、確かめられなかったこと、確認クイズ）は章の数にも量にも数えない。

## 抽象から具体へ

ページ全体も章の中も、抽象から具体へ下りる。

| 深さ | 出すもの | 出さないもの |
| --- | --- | --- |
| 1. 全体 | 何であるか、何ができるか。読み手の言葉で | 製品の用語、例の処理名、コード、数字 |
| 2. 形 | 主な部分の名前と、つながりの向き | API 名、引数、設定値、上限 |
| 3. 動き | 一例を処理名で通し、時間に沿って何が起きるか | コード、設定の書き方 |
| 4. 構造とパラメータ | 骨組みと、動きを変える代表的なパラメータ | 行ごとのコード解説 |

1章と2章は深さ1と2だけで書く。一般の形を言ってから一例を出し、一例の中で要る場面が来てから製品の用語を出す。正常の動きを見せてから、失敗、待ち、止め方に進む。

## 章立て

2部に分ける。順は入れ替えない。話題が無い章は省く。

**第1部 仕組み**（厚く書く。図は必須）

| 章 | 書くこと | 図 |
| --- | --- | --- |
| 何であるか | 一つ目の要点。公式が挙げる使いどころを一般の形で並べる | `what`。真ん中に製品、まわりに使いどころ。静止 |
| なぜ要るか | 自前だと要る部品と、それが無くなる様子。使いどころの一つを「一例」として置く | `need`。自前と、任せたあとの前後 |
| 登場人物 | 構成要素と、どこからどこへ何が流れるか | `cast`。誰から誰へ何が流れるか |
| 動きの核心 | 正常と、失敗や停止から戻る動き | `resume`。動く図 |
| 構造とパラメータ | 骨組みと、動きを変える代表的なパラメータ | `struct`。核心の図の箱が骨組みのどの塊か |
| 応用の動き | 一例を動かすのに要る、待つ、失敗、止める動き | `branch`。動く図 |

**第2部 使い始めるとき**（短く書く。表か図を一つ置き、文章は数文）

| 章 | 書くこと |
| --- | --- |
| 選び方 | 状況に対して一つを選ぶ理由 |
| 担い手 | 技術が担うものと、手元に残るもの |
| 比べる相手 | 相手の名前で、違いを主な部分の語で |
| 本番 | 手元の形から、本番で決めること。コマンドの一覧にしない |
| 上限 | 値と出典。すでに出した流れのどこに掛かるか |
| AI エージェント用の公式 skill | 「公式 skill」の節。省かない |

第2部は、二つか三つの章を一つの表にまとめてよい。図を置くなら `choice`、`owner`、`compare`、`prod`、`limit` の `data-fig` を付ける。

最後に、「チェックリスト」（書くときと動かすときに分け、各項目に章番号）、「確かめられなかったこと」、「確認クイズ」の3章を置く。見出しはこの文言を含め、目次から探せるよう必ず章（h2）にする。この3章は章の数と見出しの長さの上限に数えない。使い方や版の絞り込みは冒頭の注記にし、章にしない。

## 章の中

プレゼンの1枚と同じにする。

1. 最初の1文で、その章の結論を言う。読み手は、この1文だけ読んでも要点を拾える
2. 図。図を置く章は、結論の直後に置く
3. 図の読み方を数文。図を見れば分かることは書かない
4. 一例の動きを通す
5. 骨組みとパラメータがある章は、ここで出す
6. 囲みは key（図に無い定義）と trap（やりがちな間違い、旧版との違い、セキュリティの注意）の2種類だけ。章に一つまで
7. 出典は章の末尾に折りたたむ

話題が浅い章は 4 と 5 を省く。章末に要約を置かない。結論は最初の1文で言ってある。章への参照は「4章」と書く。§、「隣」「前述」のような作者の段取り語は使わない。

## 動き

入門の中心は動きである。時間に沿って何が起きるかが分からなければ、読み手は説明できない。

- 主な動きを、それぞれ一枚の動く図にする。正常の動きは必ず描き、失敗とやり直し、待ちは、その技術にあれば描く。文章だけで動きを説明しない
- 時間の流れは、シーケンス図の形で描く。登場人物ごとに縦の線を引き、時間は上から下へ進む。出来事は一つずつ、線から線への矢印にする。状態を行で並べた図にしない。それでは何が起きたかが見えない
- 接続が成り立つまでの出来事（相手を見つける、登録する）も矢印にする
- 一つずつ起きる出来事をまとめない。2件のデータが続けて失われるなら、矢印を2本にする
- 止まっている登場人物は、その期間だけ縦の線を切るか網掛けにする
- 点は一つが時間の順に進み、図全体を1周してから繰り返す
- 動きの核心には、その技術の動きを一文にした「核心の一文」を置き、直後に一例を同じ処理名の図で通す。途中から再開する技術なら、何が呼び直され、何が飛ばされ、どこから動き直すかを言う。そのあいだに版差や API の一覧を挟まない

## 構造とパラメータ

コードの細かい書き方は版で変わる。見せるのは骨組みと、動きを変えるパラメータである。

- 骨組みは数行にする。動く図のどの箱がどの塊かを先に言う。行ごとの解説はしない。「書き方は版で変わる」と一言添え、公式の例へリンクする
- パラメータは動きを変えるものだけを数個選び、名前、何を決めるか、動きのどこに効くか、既定値を表にする
- 読み手が手元で動かすコードがあるときは、それを一例にする。骨組みはそのファイルからの抜粋にし、ファイル名を付け、省いた行は「…」で示す。図の箱、本文の語、ログの文言を、コードの識別子と実際の実行ログに合わせる。教材のために別のコードを書かない

## 例の置き方

- 一般の形を言ってから「一例として」出す。製品の説明を例の業務の言葉で書かない。「注文処理を管理する」ではなく「長い処理を途中から続ける。注文処理はその一例」と書く
- 例は一つにし、第1部を同じ処理名で通す。章ごとに例を変えない
- 見出しと 1章の図には、例の処理名を出さない

## 用語と見出し

- 公式の語は綴りのまま書き、意味は初出の一文で日本語にする。run を「ラン」、retry を「再試行」のように置き換えない
- 読み手が知っている一般の技術用語（IP アドレス、ポート、プロセス、キュー、スレッドなど）はそのまま使う。「住所」「郵便受け」「窓口」のような日常語の比喩に置き換えない。比喩が指すものを読み手が決められず、要点がぼやける。比喩を使ってよいのは、その技術に固有で読み手の知識に対応物が無い概念だけで、そのときも同じ文で正式な語を添える
- 用語は使う章より前で定義する。1章では製品名のほかに製品の用語を使わない
- 定義する語は初出で `<dfn>` で囲む。一つの章で定義するのは3語までにする。それ以上要るなら、残りはその語が要る章まで遅らせる。一度に並んだ定義は覚えられない
- 同じ章でまとめて定義してよいのは、その章の図に一緒に出てくる語だけである。図に出てこない語は、関連が深くても使う章まで定義しない
- 取り違えやすい語は、読み手が書く言語の具体で、紛れる相手と対にして見せる。callback なら、関数を渡すこと（`handler`）とその場で呼ぶこと（`handler()`）を並べ、渡した関数を誰がいつ呼ぶかを書く
- 見出しは25字までの短い主張にする。「概要」のような区分名にせず、長い説明は章の最初の1文に回す。見出しを上から読むと要点がたどれるようにする

## 文章

- 1文に主張は一つ。結論を先に置く
- 主語と述語のある文にする。「〜ため」「〜こと」で終わる断片にしない。声に出して読んで通るかを確かめる
- 「分ける」「連携する」「管理する」などの動詞は、何をそうするのかを同じ文に書く
- 翻訳調にしない。漢語や専門語は、日常の言葉で言えるならそうする。一般的でないカタカナ語を説明の言葉に使わない
- 公式ドキュメントにも依頼にも無い文脈を足さない。たとえを事実として書かない

## 図

- 描くのは部品の名前の並びではなく仕組みである。データがどこを流れ、何が差し替わり、どこで止まるかを見せる
- 矢印には、すべて動詞のラベルを付ける（送る、受け取る、呼ぶ、見つける）
- 図ごとに、何を示す図かを `figcaption` の1文で書く
- 箱の顔ぶれとラベルは本文の語にそろえる。本文に無い箱は置かない。箱、矢印の番号、ラベルの並びを処理の順に合わせる
- 動く点は、箱の縁から次の箱の縁までの線の上だけを進む。箱の上、箱の中、箱を横切る線の上を通らない。折れ線や分岐はインライン SVG にし、線は箱の外側で止める
- SVG の文字は自動で折り返さない。箱の文字は1行を箱の幅に収まる字数にし、長ければ `text` を分けるか言い換える
- 動きのない図は静止させる。並びが順序でないときはそう書く
- `prefers-reduced-motion: reduce` のときは点を止める

## 公式 skill

読み手はその技術を AI エージェントと一緒に書くことが多い。公式の skill の有無で、エージェントが旧版の書き方を写す危険が変わる。だから無いときも章を省かない。

- 公式とみなすのは、提供元が出したものだけである。公式ドキュメントに載っているもの、提供元の GitHub organization にある `SKILL.md`、提供元の名前で出たプラグインの掲載である。第三者の skill は公式として書かない
- 章の要素に `data-agent-skills` を付け、値を「ある」「無い」「未確認」のどれかにする。確かめた場所を出典にする
- **ある**: skill ごとに、名前、何を手伝うか、どの章の話題か、対応する版を表にする。入れ方は公式の手順へリンクする。食い違えば公式ドキュメントに従うこと、script を含む skill は入れる前に中身を見ることを一言添える
- **無い**: 確認日時点で無いと書き、探した場所をリンクで並べる
- **未確認**: 何を確かめられなかったかを書き、「確かめられなかったこと」にも入れる
- 公式の MCP サーバーや `llms.txt` があれば、一行ずつ添えてよい

## 調べ方

- 対象の使い方を絞る（self-host か、使う言語と SDK の版など）。対象、版、確認日、手元の例と環境、扱わないものは、要点の直後に閉じた `<details data-scope>` で置く。`summary` は「対象と版（確認日 YYYY-MM-DD）」のように短くし、本文に開いて並べない
- 一次情報は公式ドキュメントである。主張ごとに公式の URL と原文の引用を残す。ドキュメントに無いことだけ、タグを固定したソースコードで補い、本文で「ソースコード上」と書く。どちらでも確かめられないことは「確かめられなかったこと」に入れる
- 実行の進み方、上限、既定値は、自分で公式ページを開いて原文を確かめる
- 日本語の公式ページがあれば原文とあわせてリンクする。無ければ原文だけにし、無いとは書かない

## HTML

- 単一の HTML。CSS はファイル内に置く。script は確認クイズの採点だけ。CDN、外部 JS、外部フォント、Mermaid は使わない
- 目次は章番号つきで見出しと同じ文言にし、デスクトップでは本文の右に置く
- 色は状態（正常、失敗、待ち、停止）に一色ずつ当て、数色に絞る。色だけで区別せず、ラベルか形も変える。文字はシステムフォントで、大きさは3種類まで
- `prefers-color-scheme: dark` の配色を用意する
- 狭い画面（375px）: viewport の meta を置く。`@media (max-width: …)` で目次を本文の上に移し、一列にする。ページも図も横にスクロールさせない。SVG は `viewBox` と `width: 100%` にし、箱の横並びは折り返すか縦にする。横スクロールしてよいのは `pre` と、`overflow-x: auto` で包んだ表だけ。本文中の `code` は `overflow-wrap: anywhere` で折り返す

## 確認クイズ

末尾に `data-quiz` を付けて置く。各問に章番号を持たせ、章の順に並べる。答えと、なぜかを1〜2文で返す。本文の要点を問い、引っかけにしない。

## 点検

先に `python3 scripts/check-html.py <出力 HTML>` を終了コード 0 にする。スクリプト自身は `--self-test` で確かめる。スクリプトが見るのは次である。

- 外部の script、stylesheet、CDN、Mermaid。`prefers-reduced-motion` で止まらない動き
- 目次の有無、文言、位置。「正本」、§
- 箱の上や中を通る点、箱を横切る線、SVG の箱からはみ出しそうな文字（字数からの見積もりなので、目でも確かめる）
- 第1部の `data-fig`（`what`、`need`、`cast`、`resume`、`struct`、`branch`）。省くなら `data-fig-skip`。`resume` と `branch` に動く点があるか
- `data-goals` の位置と数。`data-scope` が最初の章より前の閉じた `details` か。1章と2章のコード。`data-agent-skills` の章と値とリンク
- 量（要点、章の数、見出しの長さ、章と合計の文章量）。末尾の3章が h2 か。`<dfn>` があり、各章3語までか
- 狭い画面（viewport、`@media`、SVG の幅、図と表の横スクロール、`code` の折り返し、大きい `min-width`）

そのあと目で見る。

1. 要点だけ読んで、これは何で、どう動くかが分かるか。1章が例の業務しかできないように読めないか
2. 各章の最初の1文だけ拾い読みして、話がつながるか
3. 定義の前に製品の用語が出ていないか。読み手が知っている技術用語を比喩に置き換えていないか（クイズの選択肢も含む）。見出しと文が日本語として通るか
4. 時間の流れの図がシーケンス図で、すべての矢印に動詞があるか
5. 手元のコードがあるとき、骨組み、図、ログがそのコードと実際の出力に合っているか
6. 幅 375px と暗い配色で、図の文字が重ならず読めるか
7. 用語の初出と数字を、公式の原文と照合したか。公式 skill の結論が提供元の場所で確かめた結果か

## 入れないもの

試験対策の本にある枠（章末の演習、模擬問題、操作コマンドの章）は入れない。網羅的な API の一覧、版や環境ごとの内部の違い、行ごとのコード解説も入れない。体験を書くなら、なぜその概念が要るかを一文にする。

読み手の質問に答えた説明は、本文と図にも足す。質問が出た箇所は、他の読み手も止まる箇所である。足すときは、同じ量をどこかから削る。
