# 技術の入門教材 判断知識

`tech-intro` skill の判断知識である。手順は [../SKILL.md](../SKILL.md) にある。

## 読み手

読み手はソフトウェアエンジニアである。その技術の用語も仕組みも知らない。見て分かることを先に置き、文章は図の読み方に留める。

知らないとした分野の語と前提は、使う章より前で一文で説明するか、`data-scope` に前提として書く。プログラミング、HTTP、一般の技術用語は知っているとする。

## 要点を絞る

情報が多いほど、要点はつかみにくくなる。入門の価値は、何を書かないかで決まる。

- 書く前に、読み終えて覚えていてほしいことを3〜5個に絞る。これを要点と呼ぶ。冒頭に `data-goals` の番号付きリストで見せる
- 一つ目は「何であるか」である。製品の用語を使わず、どの分野の、何を作るための、どんな種類のものかを言う。例:「アプリの中の長い処理を、途中で落ちても続きから動かすためのサービス」「ロボットのアプリケーションを作るための開発基盤」
- 残りは、基本の動きと、使う側が間違えやすいことから選ぶ
- 本文に入れるのは、要点のどれかに効く事実だけである。詳しく知りたい人には、公式ページへのリンクで足りる
- 第1部は要点を支える順に厚く書く。第2部は、使い始めるときに要る判断だけを短く書く
- 書いたあとで、どの要点にも効かない段落、図と同じことを言う段落、同じ判断の言い直しを削る

スクリプトが量を見る。要点は5個、章は12個、見出しは25字、各章の文章は600字、文章の合計は4000字、各章で定義する語は3語までである。図、コード、表、出典、クイズは文章に数えない。末尾の3章（チェックリスト、確かめられなかったこと、確認クイズ）は章の数にも量にも数えない。

## 抽象から具体へ

ページ全体も章の中も、抽象から具体へ下りる。

| 深さ | 出すもの |
| --- | --- |
| 1. 全体 | 何であるか、何ができるか。読み手の言葉で |
| 2. 形 | 主な部分の名前と、つながりの向き |
| 3. 動き | 一例を処理名で通し、時間に沿って何が起きるか |
| 4. 構造とパラメータ | 骨組みと、動きを変える代表的なパラメータ |

1章と2章は深さ1と2だけで書く。一般の形を言ってから一例を出し、一例の中で要る場面が来てから製品の用語を出す。正常の動きを見せてから、失敗、待ち、止め方に進む。

## 章立て

2部に分ける。話題が無い章は省く。

**第1部 仕組み**（厚く書く。図は必須）

| 章 | 書くこと | 図 |
| --- | --- | --- |
| 何であるか | 一つ目の要点。公式が挙げる使いどころを一般の形で並べる | `what`。真ん中に製品、まわりに使いどころ。静止 |
| なぜ要るか | 自前だと要る部品と、それが無くなる様子。使いどころの一つを「一例」として置く | `need`。自前と、任せたあとの前後 |
| 登場人物 | 構成要素と、どこからどこへ何が流れるか | `cast`。誰から誰へ何が流れるか |
| 基本の動き | 正常と、失敗や停止から戻る動き | `resume`。シーケンス図 |
| 構造とパラメータ | 骨組みと、動きを変える代表的なパラメータ | `struct`。基本の動きの図の箱が骨組みのどの塊か |
| 応用の動き | 一例を動かすのに要る、待つ、失敗、止める動き | `branch`。シーケンス図 |

**第2部 使い始めるとき**（短く書く。表か図を一つ置き、文章は数文）

| 章 | 書くこと |
| --- | --- |
| 選び方 | 状況に対して一つを選ぶ理由 |
| 担い手 | 技術が担うものと、手元に残るもの |
| 比べる相手 | 相手の名前で、違いを主な部分の語で |
| 本番 | 手元の形から、本番で決めること |
| 上限 | 値と出典。すでに出した流れのどこに掛かるか |
| AI エージェント用の公式 skill | 「公式 skill」の節。省かない |

第2部は、二つか三つの章を一つの表にまとめてよい。図を置くなら `choice`、`owner`、`compare`、`prod`、`limit` の `data-fig` を付ける。

最後に、「チェックリスト」（書くときと動かすときに分け、各項目に章番号）、「確かめられなかったこと」、「確認クイズ」の3章を置く。見出しはこの文言を含め、目次から探せるよう必ず章（h2）にする。この3章は章の数と見出しの長さの上限に数えない。使い方や版の絞り込みは冒頭の注記に書く。

## 章の中

プレゼンの1枚と同じにする。

1. 最初の1文で、その章の結論を言う。読み手は、この1文だけ読んでも要点を拾える
2. 図。図を置く章は、結論の直後に置く
3. 図の読み方を数文
4. 一例の動きを通す
5. 骨組みとパラメータがある章は、ここで出す
6. 囲みを置くなら、key（図に無い定義）か trap（やりがちな間違い、旧版との違い、セキュリティの注意）にする
7. 出典は章の末尾に折りたたむ

話題が浅い章は 4 と 5 を省く。章への参照は「4章」と書く。

## 動き

入門の中心は動きである。時間に沿って何が起きるかが分からなければ、読み手は説明できない。

- 主な動きを、それぞれ一枚のシーケンス図にする。正常の動きは必ず描き、失敗とやり直し、待ちは、その技術にあれば描く
- 時間の流れは、シーケンス図の形で描く。登場人物ごとに縦の線を引き、時間は上から下へ進む。出来事は一つずつ、線から線への矢印にする。2件のデータが続けて失われるなら、矢印を2本にする
- 接続が成り立つまでの出来事（相手を見つける、登録する）も矢印にする
- 止まっている登場人物は、その期間だけ縦の線を切るか網掛けにする
- 基本の動きの章では、まずその技術の動きを一文で言い切り、直後に一例を同じ処理名の図で通す。途中から再開する技術なら、何が呼び直され、何が飛ばされ、どこから動き直すかを言う

## 構造とパラメータ

コードの細かい書き方は版で変わる。見せるのは骨組みと、動きを変えるパラメータである。

- 骨組みは数行にする。基本の動きの図のどの箱がどの塊かを先に言う。「書き方は版で変わる」と一言添え、公式の例へリンクする
- パラメータは動きを変えるものだけを数個選び、名前、何を決めるか、動きのどこに効くか、既定値を表にする
- 読み手が手元で動かすコードがあるときは、それを一例にする。骨組みはそのファイルからの抜粋にし、ファイル名を付け、省いた行は「…」で示す。図の箱、本文の語、ログの文言を、コードの識別子と実際の実行ログに合わせる

## 例の置き方

- 一般の形を言ってから「一例として」出す。例:「長い処理を途中から続ける。注文処理はその一例」
- 例は一つにし、第1部を同じ処理名で通す。章ごとに例を変えない
- 見出しと 1章の図には、例の処理名を出さない

## 用語と見出し

- 一つの対象は、本文、図、表、チェックリスト、クイズを通して一つの語と一つの表記で書く（Pod なら Pod、node なら node）
- 公式の語は綴りのまま書き、意味は初出の一文で日本語にする。run を「ラン」、retry を「再試行」のように置き換えない
- 読み手が知っている一般の技術用語（IP アドレス、ポート、プロセス、キュー、スレッドなど）はそのまま使う。比喩は、その技術に固有で読み手の知識に対応物が無い概念に使い、同じ文で正式な語を添える
- 部品のふるまいは、保存する、保持する、送る、返すのように動作で書く。例: DB は一意制約違反のエラーを返す
- 用語は使う章より前で定義する
- 定義する語は初出で `<dfn>` で囲む。一つの章で定義するのは3語までにする。それ以上要るなら、残りはその語が要る章まで遅らせる。一度に並んだ定義は覚えられない
- 取り違えやすい語は、読み手が書く言語の具体で、紛れる相手と対にして見せる。callback なら、関数を渡すこと（`handler`）とその場で呼ぶこと（`handler()`）を並べ、渡した関数を誰がいつ呼ぶかを書く
- 見出しは25字までの短い主張にする。「概要」のような区分名にせず、長い説明は章の最初の1文に回す。見出しを上から読むと要点がたどれるようにする

## 文章

- 1文に主張は一つ。結論を先に置く
- 主語と述語のある文にする。声に出して読んで通るかを確かめる
- 1文の中で述語ごとに動作主が替わるなら、述語ごとに誰がするかを書く。主語を最後に一つだけ書くと、全部をその主語がしたように読める。名前は登場人物の章と、シーケンス図の矢印の始点にそろえる
- 「分ける」「連携する」「管理する」などの動詞は、何をそうするのかを同じ文に書く
- 漢語や専門語は、日常の言葉で言えるならそうする
- 処理を飛ばす・無視する動きは、エラーになるか、ログが出るかを公式で確かめた範囲で書く

## 図

- 描くのは部品の名前の並びではなく仕組みである。データがどこを流れ、何が差し替わり、どこで止まるかを見せる
- 矢印には、すべて動詞のラベルを付ける（送る、受け取る、呼ぶ、見つける）
- 図ごとに、何を示す図かを `figcaption` の1文で書く
- 箱の顔ぶれとラベルは本文の語にそろえる。箱、矢印の番号、ラベルの並びを処理の順に合わせる
- 線は箱の縁から次の箱の縁までにする。折れ線や分岐はインライン SVG にする
- シーケンス図の矢印のラベルは、先頭に番号（①②…）を付けて「①送る」のように書く。番号で順序が読める
- SVG の文字は自動で折り返さない。箱の文字は箱の幅に収め、長ければ `text` を分けるか言い換える
- ラベルは箱、線、矢じり、ほかのラベルから離して置く
- 幅 375px でも図の文字が読める大きさにする。横に長い図は、同じ `figure` に狭い幅用の縦に並べた SVG を置き、`@media (max-width: …)` で切り替える
- 動きのない図は静止させる。並びが順序でないときはそう書く

## 公式 skill

読み手はその技術を AI エージェントと一緒に書くことが多い。公式の skill の有無で、エージェントが旧版の書き方を写す危険が変わる。だから無いときも、無いと書く章を置く。

- 公式とみなすのは、提供元が出したものだけである。公式ドキュメントに載っているもの、提供元の GitHub organization にある `SKILL.md`、提供元の名前で出たプラグインの掲載である
- 章の要素に `data-agent-skills` を付け、値を「ある」「無い」「未確認」のどれかにする。確かめた場所を出典にする
- **ある**: skill ごとに、名前、何を手伝うか、どの章の話題か、対応する版を表にする。入れ方は公式の手順へリンクする。食い違えば公式ドキュメントに従うこと、script を含む skill は入れる前に中身を見ることを一言添える
- **無い**: 確認日時点で無いと書き、探した場所をリンクで並べる
- **未確認**: 何を確かめられなかったかを書き、「確かめられなかったこと」にも入れる
- 公式の MCP サーバーや `llms.txt` があれば、一行ずつ添えてよい

## 調べ方

- 対象の使い方を絞る（self-host か、使う言語と SDK の版など）。対象、版、確認日、手元の例と環境、読み手に前提とする知識、扱わないものは、要点の直後に閉じた `<details data-scope>` で置く。`summary` は「対象と版（確認日 YYYY-MM-DD）」のように短くする
- 一次情報は公式ドキュメントである。主張ごとに公式の URL と原文の引用を残す。ドキュメントに無いことだけ、タグを固定したソースコードで補い、本文で「ソースコード上」と書く。どちらでも確かめられないことは「確かめられなかったこと」に入れる
- 実行の進み方、上限、既定値は、自分で公式ページを開いて原文を確かめる
- 言い切りの強さは原文に合わせる。normally、typically、usually、may、might、could、can、in many cases で書かれたことを、断定や「〜する」という指示にしない
- should を必須にも任意にも言い換えない。must を勧めに弱めない
- 本文で留保を保っても、要点や表に縮めた先で留保と対象の範囲が落ちやすい。照らし方は「点検」の 8 に置く
- 表に強さのラベルを付けるのは、公式が must、should、may を書き分けている項目だけにする。教材としての勧めにはラベルを付けず、勧めだと分かるように書く
- 日本語の公式ページがあれば原文とあわせてリンクする。無ければ原文だけにする

## HTML

- 単一の HTML。CSS と script はファイル内に置く
- 目次は章番号つきで見出しと同じ文言にする。番号は1回だけ付ける
- 広い画面では横幅を使う。ページ全体は 1200px 前後まで、本文の列は 900px 前後にする。目次は右に 200px 前後の細い列で置き、文字は本文より小さくする
- 色は状態（正常、失敗、待ち、停止）に一色ずつ当てる。色のほかにラベルか形も変える
- `prefers-color-scheme: dark` の配色を用意する
- 動きを一文で言い切った文は、本文と同じ大きさの太字にし、前後を空けて目立たせる
- 狭い画面（375px）: viewport の meta を置く。`@media (max-width: …)` で目次を本文の上に移し、一列にする。ページと図は幅に収める。SVG は `viewBox` と `width: 100%` にする。横スクロールしてよいのは `pre` と、`overflow-x: auto` で包んだ表だけ。本文中の `code` は `overflow-wrap: anywhere` で折り返す

## 確認クイズ

末尾に `data-quiz` を付けて置く。各問に章番号を持たせ、章の順に並べる。答えと、なぜかを1〜2文で返す。本文の要点を問う。

## 点検

先に `python3 scripts/check-html.py <出力 HTML>` を終了コード 0 にする。指摘には直し方が書いてある。最後に出る、出典の強さの語（normally、may、should など）を含む文の一覧は合否に数えず、点検 8 の材料にする。

そのあと目で見る。

1. 要点だけ読んで、これは何で、どう動くかが分かるか。1章が例の業務しかできないように読めないか
2. 各章の最初の1文だけ拾い読みして、話がつながるか
3. 定義の前に製品の用語が出ていないか。知らないとした分野の語を説明なしで使っていないか。同じ対象を別の語や表記で書いていないか。読み手が知っている技術用語を比喩に置き換えていないか（クイズの選択肢も含む）。見出しと文が日本語として通るか
4. 時間の流れの図がシーケンス図で、矢印の番号と動詞で順序が読めるか
5. 手元のコードがあるとき、骨組み、図、ログがそのコードと実際の出力に合っているか
6. 幅 375px と暗い配色で、図の文字が線や箱と重ならず読めるか
7. 用語の初出と数字を、公式の原文と照合したか。公式 skill の結論が提供元の場所で確かめた結果か
8. スクリプトが出典から一覧に出した、強さの語を含む引用を一つずつ、要点、本文、図の説明（figcaption と図のラベル）、表、チェックリスト、クイズの解説の対応する文と照らしたか。原文の留保と対象の範囲が落ちていないか

## 読み手の質問

読み手の質問に答えた説明は、本文と図にも足す。質問が出た箇所は、他の読み手も止まる箇所である。足すときは、同じ量をどこかから削る。
