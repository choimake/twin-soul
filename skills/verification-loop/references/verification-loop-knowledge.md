# verification-loop 判断知識

この資料は `verification-loop` skill の判断知識をまとめたものである。`SKILL.md` は使い方に留め、品質ゲート・打ち切り・渡す指示・errors 運用の詳細はこの資料を起点にする。

テンプレート:

- [../assets/review-scorecard-template.md](../assets/review-scorecard-template.md)
- [../assets/report-template.md](../assets/report-template.md)
- [../assets/errors-entry-template.md](../assets/errors-entry-template.md)
- [../config/defaults.yaml](../config/defaults.yaml)

読み方:

- 着手前は「設定の解決」「合格基準の確認観点」「品質ゲート」を優先する
- 任せるときは「実装に渡す項目」「レビューに渡す項目」を優先する
- 不合格・打ち切り時は「打ち切り条件」「errors.md 運用」を優先する
- 合否の直前は「親が成果物を見る」を優先する

`config/` には実行時の既定値（モデル・品質ゲート・ループ上限・`errors_path`）を置く。判断知識は `config/` に置かず、`references/` に置く。

## 用語

- **親**: 実装とレビューを任せ、割り振りと合否だけする本体
- **実装サブエージェント**: 実装を担当する先
- **レビューサブエージェント**: 独立レビューを担当する先
- **試行**: 実装 → レビュー → 親が見る、の 1 往復
- **ループ上限**: `max_loops`（既定 3）。試行回数がこれに達すると打ち切り対象になる
- **判定不能**: 合格基準の証拠を親が見られなかった状態。合格ではない。作業が悪い証明でもない

以降、本文はこの用語で統一する。

## 設定の解決

優先順位（上ほど強い）:

1. 呼び出し引数（タスク本文・直前指示に含まれる指定）
2. [../config/defaults.yaml](../config/defaults.yaml)
3. まだ決まっていなければ着手前にユーザーへ確認する

解決する項目:

- `implementer_model` / `reviewer_model`
- `quality_gate`（未指定時の既定は `review`）
- `max_loops`（未指定時の既定は `3`）
- `errors_path`（未指定時の既定は `.verification-loop/errors.md`）
- 合格基準（完了条件、機械的検証、レビュー観点）

### モデル指定

- モデル識別子は実行環境のツール（例: Task / Agent）が受け付ける文字列をそのまま使う
- Cursor と Claude Code など、ツールごとに識別子の形が違う。skill 側で製品固有の slug を決め打ちしない
- 実装に特定モデルを渡す必要がある場合、親のモデルをそのまま使う経路（`model` 指定が効かない）は使わない
- この会話を読まなくても足りる指示を渡す。会話の文脈への暗黙の依存は避ける

## 合格基準の確認観点

未提示または曖昧な場合、着手前に次を確認する。

- 完了条件（何ができたら終わりか）
- 機械的な検証方法（テスト・lint・型チェック・ビルドのどれを通すか）
- レビュー観点（正しさ・設計・ドキュメント整合・セキュリティの 4 点）
- 品質ゲート（下表のどれを適用するか。未指定なら成果物の性質に応じて提案し、ユーザーに確認する）
- ループ上限（設定キーは `max_loops`。未指定時の既定は 3）

確定した基準とゲートを箇条書きで提示してから着手する。以降は、この基準だけで合否を判定する。基準を勝手に緩めない。

## 品質ゲート

| ゲート     | 合格ライン | 対象                                      |
| ---------- | ---------- | ----------------------------------------- |
| draft      | 0.70       | 中間生成物・下書き                        |
| review     | 0.85       | 統合・分析結果・通常のコード/ドキュメント |
| production | 0.93       | 最終成果物・社外向け                      |

総合スコアがゲートの合格ライン以上なら合格、未満なら不合格とする。判定不能はスコアに関係なく合格にできない。不合格時の再試行・打ち切りはゲートによらず、打ち切り条件（`max_loops` 等、次節）に従う。ゲート別の再試行上限は設けない。

総合スコアの既定の算出方法は基準スコアの単純平均とする。重み付き平均が必要な場合は、手順 4（合格基準の提示）で明示する。

## 親が成果物を見る

レビュー担当のスコアカードは入力であり、合格の根拠ではない。親が見たものだけを合格の根拠にする。

見るもの:

- `git diff`。取れなければ変更ファイルの Read
- 機械的検証のコマンド出力（終了コードと本文）。会話に要約しか無ければ、親が該当コマンドを再実行して出力を残す
- 対象の実ファイル

見ないもの:

- 実装担当の「直した」「テストは通った」という自己申告
- レビュー担当の「基準を満たした」という要約だけ
- スコアカードの点数そのもの（引用箇所を実ファイルと突き合わせる前）

判定不能にする例:

- レビューが `path:行` を挙げたが、その行に該当内容が無い
- lint やテストを通したと書いてあるが、コマンド出力が無い
- 変更ファイル一覧にあるファイルを Read できない

判定不能は作業が悪い証明ではない。ループ上は不合格として扱い、修正指示は「欠けた成果物を見ろ」（どのファイル、どのコマンド）と書く。実装やスコアカード採点は親がやらない。

## 打ち切り条件

機械的に判定できるものだけを条件とする。該当したら直ちに作業を停止し、打ち切りをユーザーへ報告する。「もう少しで終わるので続行する」という判断は禁止する。

- 試行回数がループ上限（既定 3 回）に達した
- 同じ修正指示を 2 回書き足しても、同じ基準が不合格のままである
- 総合スコア 0.60 未満が 2 回続いた
- 判定不能が 2 回続いた
- レビューサブエージェントが「根拠を引用できない」と判定した箇所を、親が見ても解消できなかった
- 基準自体の変更（スコープ変更）が必要と判明した

打ち切り時に提示する内容:

1. ここまでの成果物
2. 未完了項目
3. 再開手順

## 実装に渡す項目

必ず渡す:

- 目的
- 対象ファイルと範囲
- 合格基準
- 返す形式（変更ファイル一覧と各変更の要約）
- 該当する規約スキル（例: 利用先の `.agents/skills/` 配下）を読む指示
- 確定した `implementer_model`（ツールが受け付ける形式）

過去のエラー記録（`errors_path`）に同種タスクの直近エントリがある場合は、「適用した対策」欄の内容を実装指示へ書き足す。

再試行時は、レビューの修正指示を「## 前回の問題点と修正指示」として実装指示の末尾に追記する。判定不能だった場合は、欠けていたファイルやコマンドをここに書く。

## レビューに渡す項目

必ず渡す:

- 成果物の特定方法（diff・変更ファイル一覧）
- 合格基準の明示的な列挙
- 適用中の品質ゲートと合格ライン
- 返す形式（[../assets/review-scorecard-template.md](../assets/review-scorecard-template.md)）
- 確定した `reviewer_model`（ツールが受け付ける形式）

採点の注意:

- 「良いか？」と漠然と聞かない。常に高スコアが返りやすい
- 基準ごとに 0.0〜1.0 で採点させ、根拠は親が開ける場所（ファイルと行、またはコマンド出力）に限る
- 判定は `合格 / 不合格 / 判定不能` の 3 値。判定不能は合格にできない
- 不合格時の修正指示は「〜が悪い」ではなく「〜を〜に変更せよ」の命令形で、対象ファイルと変更内容を特定させる
- レビューは毎回新しいレビューサブエージェントに任せる。実装サブエージェントの続きで自己レビューさせない

## ループ記録

各試行後、親の会話内に次を追記する。長期タスクではファイルに書き出してもよい。

```text
{試行回数, 失敗した基準, 書き足した修正指示, スコア}
```

## 合格後の変更

- 合格済み成果物へのレビューなし修正は退行の温床になる
- レビューサブエージェントの任意提案を含む改善・修正は、どんなに小さくても親が直接適用しない
- 適用する場合は新しい試行として扱い、実装を任せる → 独立レビュー → 親が見る、を必ず通す。成果物種別に応じて次を合格基準へ追加する
  - コード変更を含む場合: 修正に対応する退行を止めるテストを同時に足す
  - ドキュメント・設定のみの変更の場合: 機械的検証（lint 等）または確認手順を合格基準へ追加する
- 適用しない場合は「残課題（任意）」として報告に明記し、次回ループの入力として残す

## errors.md 運用

- 追記先は `errors_path`（既定 `.verification-loop/errors.md`）。APM の skill 展開ディレクトリには書かない
- `.verification-loop/` は Git 管理外にする
  - この skill の `.gitignore` は、skill 配下への誤配置に備えて `errors.md` を除外する
  - 利用先リポジトリのルート `.gitignore` では `.verification-loop/` を除外する（本リポジトリのルートも同様）
- 試行が 2 回以上発生した場合のみ追記する
- エントリ形式は [../assets/errors-entry-template.md](../assets/errors-entry-template.md) に従う
- エラー種別の例: `hallucination`（出典のない固有名詞・数値）/ `format_error`（指定形式との不一致）/ `context_drift`（当初目標からの逸脱）/ `tool_failure`（ツール実行の失敗）
- 同種のエラーが過去にもあれば `recurred: true` とする。対策が効いていない印になる
- ファイルには「状態: 未解消」または「状態: 対策の定着を監視中」のエントリだけを保持する
- 解消済み（修正が完了し、対策を SKILL.md のルールや退行を止めるテストへ移したもの）のエントリは、追記のタイミングで削除する
- 教訓はルール・テストに移してから消す（記録だけ消して教訓を失わない）
