# verification-loop 判断知識

`SKILL.md` の手順を補う判断知識をまとめる。手順に書いたことは繰り返さない。

テンプレートとスクリプト: [review-scorecard](../assets/review-scorecard-template.md) / [impl-report](../assets/impl-report-template.md) / [verify-report](../assets/verify-report-template.md) / [report](../assets/report-template.md) / [errors-entry](../assets/errors-entry-template.md) / [defaults.yaml](../config/defaults.yaml) / [check_evidence.py](../scripts/check_evidence.py)

`config/` には実行時の既定値だけを置き、判断知識はこの資料に置く。

## 用語

- **親**: 実装・レビュー・実行検証を任せ、割り振り・照合・裁定・合否だけする本体
- **実装／レビュー／実行検証サブエージェント**: それぞれ実装、静的な採点、機械的検証・テストの効き目の確認・動かす確認を担当する先
- **テストの効き目の確認**: 足したテストが守る実装を戻し、テストが落ちるかを見ること。落ちなければ、そのテストは何も守っていない
- **ラウンドディレクトリ**: 1 試行の指示・報告・スコアカード・コマンド記録を置くディレクトリ
- **照合スクリプト**: `scripts/check_evidence.py`。コマンドの記録（`run`）と根拠の照合（`check`）をする
- **試行**: 実装 → レビューと実行検証 → 親の照合、の 1 往復。採点し直しだけの往復も 1 試行に数える
- **判定不能**: 合格基準の証拠を親が確かめられなかった状態。合格ではないが、作業が悪い証明でもない

## 設定の解決

呼び出し引数 → [defaults.yaml](../config/defaults.yaml) → 未確定ならユーザー確認、の順に強い。

- `implementer_model` / `reviewer_model` / `verifier_model`（空なら `reviewer_model`）
- `quality_gate`（既定 `review`）、`max_loops`（既定 3）
- `errors_path`（既定 `.verification-loop/errors.md`）、`runs_dir`（既定 `.verification-loop/runs`）

モデル識別子は実行環境のツール（Task / Agent など）が受け付ける文字列をそのまま使う。製品固有の slug を skill 側で決め打ちしない。各担当には、この会話を読まなくても足りる指示を渡す。

## 合格基準の確認観点

- 完了条件、機械的検証（テスト・lint・型・ビルド・動かす確認）、レビュー観点（正しさ・設計・ドキュメント整合・セキュリティ）、品質ゲート、ループ上限
- 設定・名前・挙動を消す／変える変更では、その名前や旧挙動を語る記述をリポジトリ全体で grep してから対象範囲を決める。変更で嘘になる記述を範囲外に置かない
- 合格基準のコマンドが動かないと分かったら、成果物をそのコマンドに合わせて作り変えない。食い違いとして報告し、基準の直しはユーザーに確かめる。確かめられないときは、読み替えた基準と理由を報告に書いて進める。この読み替えは打ち切り条件の「基準自体の変更」に当たらない

## 品質ゲート

| ゲート     | 合格ライン | 対象                                      |
| ---------- | ---------- | ----------------------------------------- |
| draft      | 0.70       | 中間生成物・下書き                        |
| review     | 0.85       | 統合・分析結果・通常のコード/ドキュメント |
| production | 0.93       | 最終成果物・社外向け                      |

総合スコアは基準スコアの単純平均（重み付きにするなら手順 4 で明示する）。判定不能はスコアに関係なく合格にしない。ゲート別の再試行上限は設けない。

## 指示を渡す前に確かめる

親が書いた指示・前提・基準の誤りは、誰も確かめないまま周を消費する。

- スクリプト名は記憶で書かず、定義元（`package.json` の scripts、`mise.toml` の tasks など）で確かめる
- 未コミットの作業ツリーをレビューさせるなら、その旨と取得方法を書く
- 行数・行番号より、構造の存在を書くほうが安全である
- 調査サブエージェントの結果を写すときは、見たブランチを確かめ、引用文が base に実在するかを grep する
- 裏の取れない推測は「未確認」と書く
- 実装担当が指示の誤りで止まったら、指示を直して同じ試行をやり直す

## ラウンドディレクトリ

```text
<runs_dir>/<run-id>/
  loop.md                 # 親が書く
  round-<N>/
    instructions-{impl,review,verify}.md   # 親が書く
    impl-report.md / scorecard.md / verify-report.md
    commands/<名前>.log / <名前>.exit      # check_evidence.py run が書く
```

- `run-id` は日付とタスク名など探せる名前にし、`runs_dir` は Git 管理外に置く
- 各担当には読み書きする絶対パスを渡し、会話への返答は完了の一行にさせる
- 使い捨て worktree はラウンドディレクトリの外に作る

## 任せるときに足す指示

SKILL.md の手順 7〜9 に加えて渡す。

- 実装: 「指示していない箇所を変えるなら、変える前に理由と実測を報告に書け」。errors の「適用した対策」。再試行では末尾に「## 前回の問題点と修正指示」
- レビュー: 前の試行で棄却した指摘と理由、「同じ理由での再掲は採点対象外」。実行の結果は `verify-report.md` を読ませる（read-only のレビュー担当はテストを実行できないことがある）
- レビューの採点: 基準ごとに 0.0〜1.0、判定は `合格 / 不合格 / 判定不能`、修正指示は「〜を〜に変更せよ」の命令形。「良いか？」と漠然と聞くと高スコアが返りやすい
- 実行検証: 実装は直させない。見つけた壊れは報告に書くだけにする

## テストの効き目の確認

- 実行検証は、足したテストが守る分岐の一覧（何を、どう戻すか）を `verify-report.md` に書く。記録名は `red-` で始める
- 2 周目以降は前の周の一覧を引き継いで確かめ直す。テストが守れていない分岐が見つかれば戻し方を足してよい。テストを強くするための仕組みなので、足すことを止めない
- 戻しても挙動が変わらない（base や戻す前と同じ出力になる）戻し方は、テスト不足ではない。親が出力を並べて示せたら棄却し、その `red-` を一覧から外す。これだけを理由に次の試行へ進まない

## 照合と裁定

照合スクリプトは、根拠の表の `path:行` と引用の実在、`cmd:名前` の記録と引用、根拠に挙げたコマンドの終了コード、`red-` が落ちたかを確かめる。根拠に挙げていない記録（着手前の確認や調べ物）は参考として出すだけにする。指摘が妥当かどうかは確かめない。

毎周は読まないもの: diff 全体、成果物全体、実装担当の「直した」「通った」、レビュー担当の「満たした」、照合前の点数。

判定不能にする例: 根拠の表が無い、NG を親が一次情報で解消できない、合格基準のコマンドに記録が無い、変更ファイルを Read できない。修正指示には欠けたファイルやコマンドを書く。

棄却に使える一次情報:

- base で同じ入力が同じ出力になる（`git show <base>:<path>`、または base の使い捨て worktree で実測）
- diff に含まれない（`git diff <base>...HEAD --stat -- <path>` が空）
- 規約原文、リポジトリ内の先例の数

レビュー担当どうしの事実主張が食い違い、合否に効くなら、親がコードを引き直して裁定する。目的に効かない波及（「関連箇所も直せ」）が続くなら、スコープ外にするかをユーザーに確かめる。

## 打ち切り条件

機械的に判定できるものだけを条件にする。該当したら止めて報告する。「もう少しで終わる」での続行はしない。

- 試行回数がループ上限に達した
- 同じ修正指示を 2 回書き足しても、同じ基準が不合格のまま
- 総合スコア 0.60 未満、または判定不能が 2 回続いた
- レビュー担当が「根拠を引用できない」とした箇所を親も解消できない
- 基準自体の変更（スコープ変更）が必要と分かった

打ち切り時は、成果物・未完了項目・再開手順を示す。

## 合格後の変更

レビューなしの修正は退行の温床になる。任意提案を含む改善は、どんなに小さくても新しい試行として手順 7〜11 を通す。適用しないものは「残課題（任意）」として報告に残す。

## errors.md 運用

- 追記先は `errors_path`。APM の skill 展開ディレクトリには書かない。利用先のルート `.gitignore` で `.verification-loop/` を除外する（skill の `.gitignore` は誤配置に備えて `errors.md` を除外する）
- 試行が 2 回以上のときだけ、[errors-entry](../assets/errors-entry-template.md) の形式で追記する
- エラー種別の例: `hallucination` / `format_error` / `context_drift` / `tool_failure` / `instruction_error`（親の指示・前提・基準の誤り）/ `false_positive`（レビューの誤った減点）/ `verification_gap`（誰も拾えなかった欠陥）
- 同種が過去にもあれば `recurred: true`。対策が効いていない印である
- 「状態: 未解消」「状態: 対策の定着を監視中」のエントリだけを残す。解消済み（対策をルール・テスト・skill 正本へ移したもの）は追記のときに消す。教訓を移してから消す
- 報告では、状態欄の無いエントリと、`recurred: true` が 2 回以上ついた型を、ルールへ移す候補として挙げる
