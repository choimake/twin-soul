# 確認方法が具体か（PBI）

## ねらい

受入基準だけでは「誰が・何を見て完了とみなすか」が残ることがある。コマンドや CI による検証手順を主とする計画書ではなく、PBI では **受入判断に必要な確認方法** を短く文章化する。

## チェック観点

- 「確認方法」または同等のセクション（例: `## 確認方法`, `## 確認・レビュー`）があるか
- 確認者、確認対象、成果物（レポート等）、または記録先のいずれかが具体的か
- 「確認する」「レビューする」だけで終わっていないか

## 指摘する基準

- セクションが無い、または「確認する」「レビューする」だけで具体性が無い場合は **提案**
- セクションはあるが箇条書きが 1 行だけで、誰が何をするかが読み取れない場合は **提案**
- 受入基準が十分に具体的で、受入判断の方法が自明な場合は指摘を緩めるか省略してよい
- ユーザーストーリーやレビュー観点の列挙で確認方法がカバーされている場合は合格扱いにしやすい

## 例

### 悪い例

```markdown
## 確認方法

- 確認する
```

### 良い例

```markdown
## 確認方法

- スプリントレビューで PdM と開発リードがデモと BigQuery 上のテーブル生成を確認する
- 検証結果は `docs/report.md` にまとめ、上記受入基準をチェックリストで突合する
```

## 補足

- コマンドや CI は必須ではない。バックログドキュメントとして **受入判断の見える化** が目的
- 小さな PBI では 1〜2 行で十分。詳細な手順や変更ファイル一覧は plan file に分ける
