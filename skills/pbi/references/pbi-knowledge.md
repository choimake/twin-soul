# PBI 判断知識

この資料は `pbi` skill の判断知識をまとめたものである。`SKILL.md` は使い方に留め、PBI 生成・レビューの詳細判断はこの資料とテンプレートを起点にする。

テンプレート:

- [../assets/pbi-template.md](../assets/pbi-template.md)
- [../assets/review-output-template.md](../assets/review-output-template.md)

## この skill の役割

- PBI Markdown の品質を保証し、必須項目（受入基準、確認方法、スコープ）の漏れを防ぐ
- ルールベースのレビューで完成度を高める
- 必要に応じ Web 検索でユーザーストーリー・受入基準まわりのベストプラクティスを補う
- **他 skill やリポジトリ内の特定パスに依存せず**、下記の対象範囲だけを本資料とテンプレートで定義する

## 本 skill の対象範囲

本 skill が扱うのは **PBI 用 Markdown** のみである。次のようなドキュメントは対象外とし、同一ファイルに混在させないか、別ファイルに分ける（どのツール・skill で書くかは本 skill は規定しない）。

- 実装手順の詳細、リポジトリ内の変更ファイル一覧、CI やコマンド実行を主とする検証手順に特化した計画書

本 skill が想定する典型セクションは次のとおり。テンプレは [../assets/pbi-template.md](../assets/pbi-template.md)。

| 区分           | 内容の例                                                     |
| -------------- | ------------------------------------------------------------ |
| 主目的         | バックログアイテムとしての目的・受入基準・確認方法の明確化   |
| 典型セクション | 背景・目的、受入基準、確認方法、メモ・論点、必要時のみ参照   |

`write-file` で保存先が未指定のときは、ユーザーに保存先パスを確認してから書き込む。既定ディレクトリは設けず、特定ツール（例: `.claude/`, `.cursor/` など）に依存するパスも本 skill では推定しない。

## 抽象ブロックと PBI の対応

PBI で使う見出しは次の抽象ブロックに対応づける。テンプレ ([../assets/pbi-template.md](../assets/pbi-template.md)) もこの対応で書かれている。

| 抽象ブロック       | PBI での主な見出し例                       |
| ------------------ | ------------------------------------------ |
| コンテキスト       | 背景・目的                                 |
| ゴール／完了の定義 | 受入基準（要約またはチェックリスト全体）   |
| 確認               | 確認方法                                   |
| 本体               | メモ・論点、必要最小限の作業メモ           |
| 制約・前提         | メモ・論点                                 |
| 参照               | 参考リンク・仕様                           |

ユーザーストーリーは任意である。利用する場合は **コンテキストの直後** にブロック引用で置くと読みやすいが、依頼内容が短いときは無理に展開しない。

## 最小版への縮小

依頼やメモ用途では、既定で次の 4 つに絞る。

1. **Why**（背景・目的）
2. **What / Done**（受入基準またはゴール）
3. **Check**（確認方法）
4. **Notes**（メモ・論点）

タスクブレイクダウンは標準セクションにしない。短い作業メモで足りる場合は「メモ・論点」に含め、実装手順・変更ファイル一覧・コマンド検証が主になる場合は plan file に分ける。

フロントマターが不要な依頼では `---` ブロックを省略してよい。

## 呼び出し側が渡せる入力

- 対象 PBI の `@path`（レビュー時）
- テーマ説明（新規下書き時）
- Web 検索キーワード（明示があれば優先）
- 保存先パス（未指定ならユーザーに確認する。既定ディレクトリは設けない）
- 出力モード（`review` / `draft` / `write-file`）

未指定なら会話から妥当な既定値を判断する。必要最低限の確認だけ追加する。

## レビュールールの適用順序

`references/rules/` 配下を **ファイル名の辞書順** で適用する。

1. `must-have-acceptance-criteria.md`
2. `must-have-verification-or-agreement.md`
3. `scope-and-deliverables.md`
4. `should-have-references.md`

各ルールは個別に評価し、違反があれば優先度（重大 / 提案 / 任意）付きで指摘する。

## 優先度の基準

### 重大

- 「受入基準」に相当するセクションが無い、または空で検証不能
- 受入項目が曖昧すぎる（確認のしようがない）
- ゴール／スコープが不明で、何を達成する PBI か判別できない

### 提案

- 確認方法が無い、または「確認する」だけで具体性が無い。ただし、受入基準だけで受入判断の方法が明らかな場合は省略してよい
- 成果物・依存・スコープ外が文章上特定しづらい
- 参照・ベストプラクティスが無い、または著しく不足

### 任意

- チェックボックス形式でない、見出しレベルの揺れ
- ユーザーストーリーの有無（任意のため必須ではない）

迷う場合は `提案` を既定にする。

## Web 検索統合のロジック

1. タスク説明からキーワードを抽出する（例: INVEST、user story、acceptance criteria、Given When Then）。
2. 検索クエリは「キーワード + best practices + backlog」などとし、年度はユーザ情報の authoritative date に合わせてよい。
3. 公式・定番の解説（Atlassian、Scrum Guide 関連の二次解説など）を優先し、最大 3〜5 件に絞る。
4. PBI の「参照」セクションにタイトル付きリンクで統合する。

検索が失敗した場合や無関係な結果しか無い場合は、提案として「参照の補足が不十分」とし、ユーザーが既知の社内規約があれば追記するよう促す。

## 出力モードごとの期待

### `review`

- PBI を読み取り、`references/rules/` を適用する
- [../assets/review-output-template.md](../assets/review-output-template.md) の形式で返す
- 重大があれば修正を促し、無ければレビュー合格を明示する

### `draft`

- テーマ説明を起点に PBI 下書きを作成する
- Web 検索で補足参照を取り込みうる
- 既定では軽量テンプレートを使い、タスクブレイクダウンや詳細な実装手順は明示された場合だけ追加する
- 完成後、自動的に `review` 相当のチェック結果を添える
- 重大があれば下書きを修正して再チェックする

### `write-file`

- `draft` と同様に本文を生成する
- 保存先が明示されていればそのパスへ保存する。未指定なら、本文生成前にユーザーへ保存先ディレクトリ（またはフルパス）を確認する。ファイル名のみ未指定の場合はタスク内容から生成する（例: `fivetran-dbt-prototype-pbi.md`）
- 保存後、パスとレビュー結果を報告する

## 応答時の明示事項

対象が未指定のとき:

- 新規 PBI / 既存レビュー / ファイル書き込みのどれかを短く確認する

本 skill を実行するときは **他 skill を読みに行かない**。関連する別ドキュメントがある場合は、ユーザーが `@path` で渡す。

`scripts/` を pbi skill に追加しない判断をした理由:

- 実行補助がなくてもテンプレとルールで運用できるため。繰り返し整形や検証が必要になった時点で改めて追加を検討する。
