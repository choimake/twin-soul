# PBI 判断知識

## 対象範囲

扱うのは PBI 用 Markdown だけ。実装手順の詳細、変更ファイル一覧、CI やコマンド実行を主とする検証手順は PBI に混ぜず、plan file に分ける。

ユーザーストーリーは任意。使うなら「背景・目的」の前にブロック引用で置く。依頼が短いときは無理に展開しない。

## 最小版

既定では次の 4 つに絞る。

1. **Why**（背景・目的）
2. **What / Done**（受入基準またはゴール）
3. **Check**（確認方法）
4. **Notes**（メモ・論点）

タスクブレイクダウンは標準セクションにしない。短い作業メモなら「メモ・論点」に含める。フロントマターが不要な依頼では `---` ブロックを省いてよい。

## 優先度の基準

### 重大

- 「受入基準」に相当するセクションが無い、または空で検証不能
- 受入項目が曖昧すぎる（確認のしようがない）
- ゴール／スコープが不明で、何を達成する PBI か判別できない

### 提案

- 確認方法が無い、または「確認する」だけで具体性が無い。ただし、受入基準だけで受入判断の方法が明らかな場合は省略してよい
- 成果物、または依存がある場合のその依存が文章上特定しづらい
- 参照が要る題材で、参照・ベストプラクティスが無い、または著しく不足
- 受入基準がチェックボックス形式でない

### 任意

- 見出しレベルの揺れ
- 隣接する作業との境界が読み取れず、スコープ外が明示されていない
- ロールや価値が本文から読み取りにくく、ユーザーストーリーの形にすると伝わりやすい

迷う場合は `提案` を既定にする。

## 参照

参照が要る題材では公式・定番の解説を優先し、3〜5 件に絞って「参考リンク・仕様ドキュメント」に入れる。検索で適切なものが見つからなければ、`提案` として「参照の補足が不十分」と指摘し、社内規約があれば追記を促す。

## 出力

- `draft` / `write-file` では、下書きに `review` 相当のチェック結果を添える。重大があれば直してから再チェックする
- 保存先の既定ディレクトリは設けない。特定ツール（`.claude/`、`.cursor/` など）のパスも推定しない。ファイル名だけ未指定なら内容から付ける（例: `fivetran-dbt-prototype-pbi.md`）
- 他の skill を読みに行かない。関連文書はユーザーが `@path` で渡す
