# GCP Security Baseline

## 目的

小規模チーム・個人が Google Cloud の環境を構築・見直す際に、最低限のセキュリティ対策と予算アラートを確認する。設定は自動適用しない。

## 使う場面

- プロジェクト・組織の新規作成や初期設定の見直し
- Terraform の google provider を使ったコードの確認
- 予算アラート、IAM、SA キー、監査ログなどの確認漏れの点検

## 手順

1. 対象のプロジェクト・課金アカウント、組織（Organization）の有無、Terraform コードの有無を確かめる。
2. 確認を始める前に [references/checklist.md](references/checklist.md) を読む。
3. コードがあれば各項目のリソース・属性を探す。組織がない構成では、組織ポリシーの代わりに `auto_create_network`、`google_project_default_service_accounts`、バケット属性など、チェックリストにあるリソース側の設定で判定する。代替がない組織専用項目は対象外とする。
4. 手作業の項目、コードの外に条件が残る項目はユーザーに確認する。認証情報・秘密の値は読まず、有無と保管方法だけ確認する。
5. 次の判定規則で全項目を判定し、根拠とともに表で返す。「参考（チェックしない）」節は判定しない。

## 判定規則

- 済: その項目の「済の条件」をすべて満たす。根拠には条件ごとの内訳を書く。推測で「済」にしない。
- 要対応: 条件のどれかに分かっている不備がある。不備と不明が両方ある場合も「要対応」とし、不明は注意欄に残す。
- 要確認: 判定を左右する情報が足りない。判定に影響しない不明点だけなら、判定を変えず注意欄に書く。
- 対象外: 確認する対象が無い（VM が無い、製品を使っていない）、または組織やプランの条件で使えないと分かっている。理由を書く。プランで使えるか不明なら「要確認」とする。
- コードだけで判定する場合、コードで確かめられる条件をすべて満たし、コードの外に条件が残らない項目だけ「済」とする。根拠に「コード確認（実環境への適用は未確認）」と書く。コードの外に条件が残る項目は「要確認」としてユーザーに聞く。ただし、既知の不備があれば「要対応」を優先する。
- 不明点は「公式に記載なし（調べた範囲）」「未確認（調べていない）」「利用環境の情報不足」に分ける。最後の区分は、コードやユーザーの回答だけでは利用環境の状態を判断できない場合に使う。

## 期待する出力

表の前に、確認の種類（コード点検か実環境の確認か）、確認した範囲（対象、組織の有無、コード・ユーザーの回答）、確認日を書く。

| 項目 | 判定 | 根拠 | 注意・未確認 |
| --- | --- | --- | --- |
| チェックリストの項目名 | 済 / 要対応 / 要確認 / 対象外 | 条件ごとの設定・回答（ファイル:行 またはユーザーの回答）、対象外の理由 | 不備、不明点とその区分 |

## 検証

- 全項目に判定があり、「済」には確認範囲に応じた根拠、「対象外」には理由がある。
- 未確認の Terraform 対応や実環境の状態を推測で断定していない。
- 組織の有無とリソース側の代替を区別し、参考節を判定していない。
- 設定変更・自動適用は実行していない。
