# 1 本の文書の目次例・対象外・未決事項（貼り付け用）

要求定義ルールの第 5.1 節・第 5.5 節・第 5.6 節に相当するコピー用ブロックである。

## 5.1 1 本の文書の目次例（枠の並び）

一意 ID の列は置かない。区切りは見出しと下記のブロックで足りる。1 本の文書にまとめる場合は、階層ごとに第 2 レベル見出し（`## ビジネス要求` 等）の直下に、1 件を第 3 レベル見出しと枠で書くと追いやすい。

```markdown
# （プロダクト名） 要求

## 対象外 / 非目標

（5.5 の例を参照。やらないことの列挙）

## 未決事項・リスク・前提

（5.6 の例を参照。合意済み要求とは分ける）

## ビジネス要求

（5.2 を繰り返し）

## ステークホルダー要求

（5.2 を繰り返し）

## ソリューション要求

### 機能

（5.2 を繰り返し）

### 非機能

（5.2 を繰り返し。観点の表は第 6.4 節）

## 移行要求

（5.3 を繰り返し）
```

第 3.5 節の趣旨に合わせ、対象外と未決事項は階層要求の前に置くと、誤解の起き方を抑えやすい。プロダクトに合わせ順序を入れ替えてもよい。

## 5.5 対象外 / 非目標（貼り付け用の例）

1 本の文書の冒頭近く用。箇条書きで足りる。合意に含めない期待を、のちのトラブル源にさせない。

```markdown
## 対象外 / 非目標

- 今回のリリースでは扱わない能力・ユーザー層
- 意図的に採用しない技術・連携
- 顧客や社内が「入っていると感じがち」だが、含めないこと
```

## 5.6 未決事項・リスク・前提（貼り付け用の例）

合意済みの要求本文とは別に、横断的な不確実性を置く。1 行に空欄を置かない（第 4.1 節と同じ。該当しなければ「該当なし」と書く、または行ごと省くが、省くときは節の導入文で理由を示す）。列は、チームのしきたりに合わせて増減してよい。

```markdown
## 未決事項・リスク・前提

| 事項     | 内容・依拠                            | オーナー | 次の合意日または次アクション |
| -------- | ------------------------------------- | -------- | ---------------------------- |
| 例: 法務 | 利用規約の表現が確定待ち              | 山田     | 〇月定例のあと               |
| 例: 技術 | 外部 API の rate limit が未測定       | 佐藤     | スパイク後のレビュー         |
| 例: 顧客 | 導入形態（SaaS / オンプレ）の回答待ち | 営業     | 顧客回答 SLA に基づく        |

前提（このプロダクトが成り立つ条件）:

- 例: 現行の ○○ 契約が継続する
```

表が重ければ、箇条書きと「オーナー／期限」だけの短い行に置き換えてよい。
