# 要求定義のルール

本書は、小規模なプロダクト開発において、要求に何を書き、どの基準で整えるかの最小公約数を定める。国際的な枠組み（BABOK、ISO/IEC/IEEE 29148 等）の趣旨に沿うが、国際標準の全文に準拠する登録用ドキュメントではない。

エージェントで本 skill を使う場合、根拠・優先度・オーナー・出典・受入基準の前提は、事実上、プロダクトオーナー・依頼者・現場・関係者などから得たインプット（または、そうした合意の記されたドキュメント）に立脚する。当て推量で埋めない。

取れなければ第 4.1 節の「未定（理由＋期限）」に寄せ、あわせて利用者（ユーザー）へ足りない事実・判断を尋ねる。利用者が仮定で進めてよいと明示したときだけ仮置き可とし、その旨を文面に示す。

## 1. 目的と適用

次の方針を採る。

目的: 合意可能な要求とし、設計・実装・受入の判断材料を揃える。

対象: 1 プロダクト／少数チームを想定する。章立てと箇条書きで追える規模を前提とする。

次の 3 点を満たせば、次工程（設計・スプリント計画・テスト方針）に渡す準備が足りる、とする。複数人が参照し、削減・遅延・受入の意思決定に使う前提である。

1. 階層が揃い、どの課題のための能力かが読み手に伝わること。
2. 1 件の要求ごとに、必須および原則必須の属性（第 4.1 節・第 4.3 節以降）が揃うこと。原則必須の項目は、第 4.1 節のとおり空欄にせず、未定のときは理由と決定期限を残す。
3. ソリューション層の要求については、少なくともどの上位の意図（ビジネス要求／ステークホルダー要求）に応えるかが、見出し・文章から辿れること。

大規模化や契約品質が求められた場合は、一意の要求 ID の付与や形式要件の拡充を別途検討する。本ルールでは ID を必須とはしない。

## 2. 用語（要求の層）

### 2.1 BABOK に近い 4 層＋移行

各層の意味は次のとおりである。並びは、抽象度の高い順である。

- ビジネス要求: なぜ行うか、何を以て成功とするか。目的・成功指標・解決したい事業上の課題を書く。
- ステークホルダー要求: 利用者・関係者のニーズ。現場の期待する働き。文脈・主要な利用シナリオの骨子を書く。
- ソリューション要求: 上記を満たすソリューションに備えてほしい能力と品質。機能要求と非機能要求に分けて扱う。
- 移行要求: 旧状態から新状態へ移行する期間に限り必要な事項。移行手順、教育、併用運用、データ移行の条件など。正規稼働後は不要になってよい内容をここに置く。

ソリューション要求のうち、次の区分を使い分ける。

- 機能要求: 振る舞い、情報の扱い。例は承認フロー、検索、出力である。
- 非機能要求: 測定可能な条件で書く。主観表現だけで終えない。小規模プロダクトほど、暗黙の品質要求がのちに不具合や運用負債になる。観点ごとに要求を定めるか「該当なし」と明記する。観点のチェック一覧は、第 6.4 節に置く（用語章では層の意味にとどめる）。

### 2.2 ISO/IEC/IEEE 29148 の文書イメージとの対応

国際標準 29148 では、成果物の型としてビジネス要求仕様（BRS）、ステークホルダー要求仕様（StRS）、システム要求仕様（SyRS）、ソフトウェア要求仕様（SRS）などが整理される。小規模では 1 本のドキュメントに階層を見出しで分けてもよい。本ルールの層と、29148 側のイメージの対応は次のとおりである。

- ビジネス要求: BRS。目的に近い OpsCon 相当の文脈を併せて書いてもよい。
- ステークホルダー要求: StRS。
- ソリューション要求（システム／ソフトのまとまり）: SyRS または SRS 相当の章。
- 移行要求: 移行期に限る別節。標準名そのものより、移行のための一時的な合意事項として扱う。

## 3. 階層別の書き方

層ごとに、多めに書く内容と、控えめにする内容を分ける。

### 3.1 ビジネス要求

- 多めに書く: 測定可能な目標。指標に期限を付けられるなら付ける。前提となる制約（法令、予算感など）。
- 控えめに: 画面や API の詳細。ここでは「何のためか」までとする。

### 3.2 ステークホルダー要求

- 多めに書く: 誰の、どの状況でのニーズか。重要な利用の流れ（箇条書きで可）。
- 控えめに: 内部設計。ソリューション層に回す。

### 3.3 ソリューション要求

- 多めに書く: システムに期待する能力。品質は試せる表現にする。どの上位要求（少なくともビジネス要求／ステークホルダー要求の意図）に応えるかを、1 件の要求に紐づけて書く（後述の「上位からの紐づき」参照）。
- 控えめに: 機能と非機能を同一の箇条書きに混在させない。同じ章内でもラベルで分ける。

### 3.4 移行要求

- 多めに書く: 切替前後の責任分界。学習・サポート。データ取り扱い。ロールバック方針。移行中だけの約束事に限る。
- 必ず明記: いつ（どの段階）まで有効で、その後は通常運用の要求に戻るか。

### 3.5 階層の外に置く章（対象外・非目標、未決事項）

ビジネス要求〜移行要求は「合意した範囲内の、やること」に焦点を当てる。次の 2 種類の章を、同じドキュメント内の別節として持つと、次工程の誤解が減る。要求 ID の列がなくても、見出し名で区別しやすい。

- 対象外 / 非目標: スコープに含まない能力、意図的にやらないこと、顧客や関係者がのちに「書いてあると思っていた」となりうる事項を、やらないと明文化する。箇条書きで足りる。
- 未決事項・リスク・前提: 合意した要求の本文とは別に、まだ揺れている外部依存、法務確認待ち、技術的実現性の未検証、顧客・ベンダの回答待ち、プロダクト存続の前提（例: 利用できる API の継続）を一覧する。合意「済みの要求」では表現しきれない不確実性を、削減・遅延の判断材料に置く。各行に、内容・オーナー・次の合意の期限（または次アクション）を残す。空欄の行を置かない（第 4.1 節と同じ考え方）。

第 5.1 節の目次例と、第 5.5 節・第 5.6 節にテンプレ例を示す（`assets` 参照）。

## 4. 1 件の要求に含める属性

一意の要求 ID は必須としない。区別は章・見出し・箇条書きの位置で足りる。必要なら短い見出し名を付ける。スコープの削減・優先度の衝突・説明責任の所在を、属性で埋め切れることを目指す。

### 4.1 属性の記入（未定の統一ルール）

本書で「原則必須」とし、すぐに値が入らない場合があっても、次を守る。読み手に「空欄＝未着手でよい」や「空欄＝不要」と解釈させない。

- **空欄にしない。** 行は残す。
- 値が出ないまま次工程に渡す場合は、未定（または TBD 等、チームで定めた表記）と明記し、なぜ未定か（法務待ち、技術実験の結果待ち、顧客回答待ち、等）と、いつまでに再び記入するか（会議日、リリース前のマイルストーン、回答 SLA 等）を書く。

この手続き（未定の見せ方）を、少なくとも優先度、担当／オーナー、出典に一様に適用する。上位要求からの紐づきと検証方法のメモは、どの層で必須に近いかが第 4.5 節・第 4.6 節で異なる。いずれの属性も、埋め切れなければ空欄ではなく、上記の未定（理由＋期限）に寄せる。

用語上、「原則必須」は、合意可能な限り全件に記入するが、上記の未定ルールで欠損の見え方を揃える、という意味で用いる。どの層のどの属性に付けるかは、第 4.3 節以降と第 4.6 節で定める。「必須に近い」は、ソリューション層の特定の属性に付ける。埋め切れなければ未定ルール、という意味で用いる。

### 4.2 全件の最低限

次の 3 点は、どの層の要求であれ揃える。

- 記述: 解釈が一つに落ちる短い文にまとめてよい。ただし「一文」に押し込む必要はない。主体・条件・振る舞い・対象・例外が読み手に伝わることを優先し、必要なら複数文に分ける。条件・例外は箇条書きの下位項目に分けてもよい。曖昧語の扱いは第 8 節を参照する。
- 根拠: なぜ必要か。後に削る・遅延する判断ができる材料にする。
- 受入基準: 何をもって満たしたとみなすか。数値、再現手順、許容差など、客観的に確認できる条件にする。設計・テストの入力に直結しうる形とする。29148 の要求検証（verification）の考え方と揃えてよい。

### 4.3 原則必須（次工程の判断に直結するため）

次の 2 点は、スコープの割り当て（何を削るか・後回しにするか）と、説明責任（誰が合意内容を説明し、変更の窓口になるか）に直結する。第 4.1 節の未定ルールに従い、空欄にせず、決め切れなければ未定（理由と期限）を書く。

- 優先度: 全体の中での相対的重要度。トレードオフのときに「残す・落とす」の材料にする。Must / Should / Could 等、チームで定めた段階の語を一貫して用いる。
- 担当／オーナー: その要求の説明責任を負う者。ロール名でよい。合意内容への問い合わせ口とする。

### 4.4 出典

- 出典: 第 4.1 節に従い、原則として常に行を埋める。争いの起きる内容、法規制・顧客約束、外部監査の対象となりうる内容は、出典元の明記を事実上必須とする。得られない段階では未定（理由と期限）とする。誰の発言か、どの会議・決定か、どの規程・チケットか。

### 4.5 ソリューション要求に加えて（トレーサビリティ）

ソリューション層（機能・非機能）の各要求に、次を主として扱う。後工程で「この能力はどの事業上の意図に対応するのか」が辿れないと、不要論や優先度の再交渉ができず、要求を削減しにくい。いずれも第 4.1 節の未定ルールを適用する。ビジネス要求・ステークホルダー要求の行にも検証方法のメモを付けてよい（推奨。第 4.6 節）。その場合も空欄にせず、未定にする。

- 上位要求からの紐づき: 少なくとも、対応するビジネス要求（必要ならステークホルダー要求）の見出し名または要約一行でよい。ID がなくても、章立て上で一方向に辿れること。まだ紐づけが曖昧なら、なぜ曖昧かと、いつ紐づけを確定するかを書く。
- 検証方法のメモ: 受入基準に対して、主としてテスト・実演・目視（検査）・分析のどれで確認するか。テスト設計・バックログ上の受入作業の入口とする。すぐに決まらなければ、第 4.1 節と同形式で未定にする。本項は、ソリューション層では原則必須に近い扱いとし、ビジネス層・ステークホルダー層では推奨とする。いずれも空欄にしない（第 4.6 節）。

### 4.6 層早見

「原則必須／必須に近い」の運用上の意味は、第 4.1 節のとおり。空欄は使わず、埋め切れなければ未定（理由＋期限）。

| 属性                 | 全層                                   | ソリューション層                 |
| -------------------- | -------------------------------------- | -------------------------------- |
| 記述・根拠・受入基準 | 必須                                   | 同左                             |
| 優先度・オーナー     | 原則必須（未定ルールあり）             | 同左                             |
| 出典                 | 原則必須（争点等は事実上必須。未定可） | 同左                             |
| 上位からの紐づき     | 上の層で自明なら短くてよい             | 必須に近い（未定可、理由＋期限） |
| 検証方法のメモ       | 推奨（行を置く場合は空欄にしない）     | 原則必須（未定可、理由＋期限）   |

## 6. 品質基準

### 6.1 バックログ単位（ユーザーストーリー、PBI 等）の INVEST

Bill Wake の助記法であり、反復的に切る単位の品質に用いる。正式な全仕様の代替にはならない。各文字の含意は次のとおりである。

- I（Independent）: 他の項に強く依存せず、まとまりとして評価・優先しやすいこと。
- N（Negotiable）: 会話の余地があり、解決策を先に固めて閉じないこと。
- V（Valuable）: 価値の主体（ユーザー／事業）が分かること。
- E（Estimable）: 粗くても、見積りの大きさが想像できる具体度であること。
- S（Small）: 短い期間で完了できる大きさであること。
- T（Testable）: 受入のイメージが持てること。主観の一語だけで終えないこと。

### 6.2 層に共通して意識すること

次の観点を揃える。

- 単一性: 1 件は 1 義務。詰め込みすぎたら分ける。
- 非曖昧: 解釈の幅を狭める。詳細は第 8 節を参照する。
- 一貫性: 上の層の目的と矛盾させない。
- 試験可能性: 受入基準と検証方法のメモを接続し、テスト・受入作業の入力にできること。
- 紐づき: 特にソリューション層では、事業上の意図（第 4.5 節）に沿う。要求 ID に頼らず、見出し名・要約行で辿れること。

### 6.3 小規模でも弱めない前提

本書の読み手は、のちにドキュメントを改訂し、他者が設計・テストを進める。属性が欠けたまま次工程に渡ると、削減・遅延・受入の判断が名指しの担当者と優先度なしに滞る。第 4.1 節・第 4.3 節・第 4.5 節で、空欄を許さない運用（未定の定型）に寄せるのは、その詰まりを避けるためである。

### 6.4 非機能要求の観点チェックリスト

第 2.1 節で述べた各観点を、ここに一覧する。用語定義（第 2 章）は軽くし、具体の網羅は本節で扱う。プロダクトごとに、下表の行に対し（表を複製し）「要求の要約」または「該当なし」と書いた一覧を 1 枚持つ。未記述の行を残さない。ドメインに応じて行を追加する。保守性、使いやすさ等、第 2.1 節で言及した語も、同様に「書く」か「該当なし」かを決める。

| 観点の例         | メモ（書く内容の例）                             |
| ---------------- | ------------------------------------------------ |
| 性能             | 応答時間、スループット、同時接続。               |
| 可用性           | 目標稼働率、計画停電、メンテナンス窓。           |
| セキュリティ     | 認証・認可、脅威の想定、脆弱性対応。             |
| プライバシー     | 個人情報の取り扱い、同意、第三者提供。           |
| 監査ログ         | 誰が何をいつ変更したか、保存期間。               |
| 運用・監視       | ヘルスチェック、通知、アラート、SLO/SLA の接続。 |
| アクセシビリティ | 利用可能な範囲、標準・ガイドラインへの準拠。     |
| データ保持／削除 | 保存期間、消去、エクスポート。                   |
| 障害時の振る舞い | 退避、読み取り専用、手続き。                     |

上表は網羅的な標準名簿ではない。

## 7. 迷ったとき

次の順で層を決める。

1. 期間限定の移行の話か: 移行要求の節に書く。
2. 何のためか、何を以て成功とするか: ビジネス層に書く。
3. 人が何をしたいか: ステークホルダー層に書く。
4. システムが何をし、どの品質か: ソリューション層に書く。
5. 層がまだ曖昧なら: 受入基準を先に書き、そこから一段だけ抽象化して上の層を足す。

## 8. よくある落とし穴

次の点に注意する。

- 曖昧語: 「速い」「安全」「使いやすい」等だけで終えない。指標、対象、条件（回線、負荷、端末）を受入基準に落とす。
- 使いやすさ: 非機能の一行に「使いやすい」だけ置かない。学習時間、主要タスクの完了率、操作手数、支援の有無など、測定または観測手順のある表現に寄せる。
- 合意のない「したまま」: 受入基準を置かないまま、作業の実施だけで区切らない。少なくとも、結果として確認できる条件にする。
- 移行と恒久: 移行期の特例と、恒久的な運用ルールを混ぜない。章を分け、移行要求に有効期間または廃止条件を書く。
- 対象外の未記載: 第 3.5 節・第 5.5 節の「対象外 / 非目標」を空にし、合意ドキュメントに「やらないこと」が書かれていない。のち「書いていないが期待されていた」という摩擦の元になる。少なくとも箇条書きで明記する。
- 未決事項の散在: 法務・技術スパイク・顧客回答待ちが、会話の中だけに残る。第 3.5 節・第 5.6 節の未決事項の節に集約し、第 4.1 節と同様に行を空にしない。

## 10. 執筆上の方針（本書のスタイル）

社内向け手順・規程に近い可読性を優先し、次を原則とする。フューチャー株式会社有志のテクニカルライティングガイドラインや、JIS Z 8301 系でいう用字用語の思想に倣う。

- 文体: 「である」調で一貫させる。箇条書きの見出し相当の語は、可能な限り体言止め（名詞句）にする。
- ブロックの導入: リストや見出しの直前に、そのブロックの役割を示す文を 1 文置く（読み手が箇所の意図を掴めるようにする）。
- 並列の情報: 抽象度の揃った要素だけを同じ階層に並べる。必要なら階層を一段深くし、一対一で説明をぶら下げる。
- 一文の長さ: 一義に寄せ、長くなる場合は文を分ける。二重否定は避ける。
- 箇条書きの表記: 本書の説明文（第 1〜4 節、第 6 節以降）では、短いラベルと 1 文の説明を並べるときに半角の「: 」（コロン＋半角スペース）を用いてよい。URL 内のコロンは除く。一方、第 5 節のコピー用テンプレは、記述欄に複数文・複数行を当てる前提のため、項目名にコロンを付けない。
- 未定と空欄: 属性の欠損の見え方は、第 4.1 節に従い、空欄ではなく未定（理由と期限）で揃える。
