# Cloudflare Security Baseline

## 目的

小規模チーム・個人向けに、Cloudflare のアカウント・ゾーン構築時に確認する最低限のセキュリティ対策と請求・使用量の通知を整理する。

## 使う場面

- アカウント・ゾーンを新しく作る、または初期設定を見直すとき
- cloudflare/cloudflare provider v5 系の Terraform コードを確認するとき
- 2FA、API トークン、請求通知、SSL/TLS、DNS、オリジン保護の設定漏れを確認するとき

## 手順

1. 対象アカウント・ゾーン、料金プラン（Free / Pro / Business）、Pay-as-you-go か、利用製品、Terraform コードの有無を確かめる。
2. 確認を始める前に [チェックリスト](references/checklist.md) を読む。
3. コードがあれば各項目のリソース・属性を探す。手作業の項目とコードで判定できない条件はユーザーに確認する。
4. 次の判定規則に従い、項目ごとの判定と根拠（ファイル:行、またはユーザーの回答）を表で返す。チェックリスト末尾の「参考（チェックしない）」は判定しない。

公式に推奨値が無い項目は「公式の記述」と「運用上の判断」を分ける。設定の変更や自動適用は行わない。認証情報・秘密の値は読まず、有無と保管方法だけ確認する。バックアップコードの値も集めない。

## 判定規則

- 済: その項目の「済の条件」をすべて満たす。根拠に条件ごとの内訳を書く。推測で「済」にしない。
- 要対応: 条件のどれかに、分かっている不備がある。不備と不明が両方あれば「要対応」とし、不明も注意欄に残す。
- 要確認: 判定を左右する情報が足りない。判定に影響しない不明点だけなら判定を変えず、注意欄に書く。
- 対象外: 確認する対象が無い、その製品を使っていない、組織やプランの条件で使えないと分かっている、のいずれか。理由を書く。プランで使えるか不明なら「要確認」にする。
- コードだけで判定するときは、コードで確かめられる条件をすべて満たし、コードの外に条件が残らない項目だけ「済」にする。根拠に「コード確認（実環境への適用は未確認）」と書く。コードの外に条件が残る項目は「要確認」にしてユーザーに聞く。ただし、分かっている不備があれば「要対応」を優先する。
- 不明点は「公式に記載なし（調べた範囲）」「未確認（調べていない）」「利用環境の情報不足」に分ける。「利用環境の情報不足」は判定時に使い、ユーザーに確認する内容を書く。

## 期待する出力

表の前に、確認の種類（コード点検か実環境の確認か）、確認した範囲（対象アカウント・ゾーン、料金プラン、利用製品、コードの範囲）、確認日を書く。

| 項目 | 判定 | 根拠 | 注意・未確認 |
| --- | --- | --- | --- |
| 項目名 | 済 / 要対応 / 要確認 / 対象外 | 条件ごとの内訳と出典、対象外なら理由 | 不明点の区分と確認内容 |

## 検証

- 全項目に判定と根拠があり、確認していない設定を「済」にしていない
- プランによる対象外と、情報不足の「要確認」を区別している
- 公式の記述と運用上の判断を区別し、通知を利用停止の仕組みとして扱っていない
- 設定を変更せず、認証情報の値を出力していない
