# Universal Code Reviewer 判断知識

この資料は `universal-code-reviewer` skill の判断知識をまとめたものである。`SKILL.md` は使い方に留め、レビュー時の境界判断、優先度付け、出力の扱いはこの資料とテンプレートを起点にする。

テンプレート:

- [../assets/review-output-template.md](../assets/review-output-template.md)

## この skill の役割

- コードレビュー時に毎回見る汎用ルールをそろえる
- コンテキスト爆発を避けるため、最初にスコープを固定する
- 個別ルールの本文は `references/rules/` に置き、レビュー時の横断的な判断ロジックだけをこの資料に置く

## 呼び出し側が渡せる入力

- レビュー対象の `@path`
- 「差分だけ」「PR の変更だけ」のようなスコープ指示
- 特に見たい論点やルール名
- 会話中に貼られたコード断片

未指定なら、この skill が会話から妥当な既定値を判断する。必要最低限の確認だけを追加する。

## 対象と探索の絞り方

1. `@path` が指定されていれば、その範囲だけをレビュー対象にする。
2. `@path` が無ければ、まずレビュー対象の `@path` 指定を依頼する。
3. ユーザーがスコープ指定に応じない場合は、会話で明示されたファイルやコード断片だけを対象にする。
4. 「差分だけレビューする」は明示指示がある場合に限る。明示が無ければ、勝手に `git diff` ベースへ寄せない。
5. 参照先や周辺設定を見ないと判断できない場合だけ、追加で見たいファイルと理由を示してスコープ拡張を提案する。
6. 追加情報が得られない場合も、現スコープで確実に言える指摘は先に返し、不確実性を明記する。

## レビューの進め方

1. スコープ内の各ファイルを確認する。
2. `references/rules/` 配下の個別ルールドキュメントをファイル名順で適用する。
3. ルールごとに違反があるかを見て、必要なら複数ルールにまたがる指摘もまとめる。
4. 他所が壊れうる変更なら、安全だと言える1事実を実行で示す。判断は「影響範囲」を参照する。
5. 修正案が短く明確な場合だけ、その場で最小限の修正案を付ける。

## 影響範囲

適用:

- 挙動が変わる変更
- 影響範囲、他所が壊れる、blast radius の依頼

非適用:

- コメント・命名・TODO だけの静的レビュー

証明:

- 実コードを呼ぶテストかスクリプトを実行し、結果を残す
- 呼び出しの列挙や説明だけでは足りない
- 示せないなら未証明と書く。証明したように書かない

## 優先度の基準

### `重大`

- 誤解、不具合、事故につながり得る
- コメントや命名が実際の挙動と矛盾している
- 放置 TODO が仕様の穴や未完の設計判断を示している

### `提案`

- 直すと保守性や可読性が上がる
- 自明なコメントの整理や、短い Why not コメントの追加が有効
- 構造変更までは不要だが、軽い改善余地がある

### `任意`

- 好みの範囲で影響が小さい
- 今回直さなくても大きなリスクは増えない

迷う場合は `提案` を既定にする。

## 修正案を付ける基準

- `重大` の指摘には原則として修正案を付ける
- 1〜3 行程度の小修正で改善できる場合は修正案を付ける
- 大きな設計変更が必要な場合は、変更方針だけを示して無理に具体コードを書かない

## 出力の組み立て方

- 指摘はファイル単位でまとめる
- 指摘が複数ある場合は `重大`、`提案`、`任意` の順で並べる
- 各指摘で `Rule`、`Priority`、`Issue` を明示する
- `Fix` は必要な場合だけ付ける
- 行番号や範囲は分かるときだけ添え、無理に精密化しない
- 追加で確認したいファイルがある場合は、指摘の後に理由付きで列挙する
- 指摘が無い場合は「指摘なし」を明示し、未確認範囲や残るリスクがあれば添える
- 他所が壊れうる変更では、安全だと言える1事実の証明、または未証明を残す

## 指摘が無い場合の返し方

- 「今回確認した範囲では重大な指摘は見当たらない」のように、スコープ付きで明示する
- 未確認の依存先、設定、テストがあれば残るリスクとして短く添える
- 何も無い場合でも、どの範囲を見た結果なのかは残す

## 応答時の明示事項

- スコープ未指定時は、まず `@path` 指定を依頼する
- 現スコープで判断できることと、判断できないことを分けて書く
- 追加スコープが必要なら、読みたいファイルと理由を短く添える
- 個別ルールドキュメントが増えても、詳細は `references/rules/` 配下の各 Markdown を参照し、この資料には判断ロジックだけを残す
- この skill の `references/` は skill ローカルの判断観点であり、その中で個別ルール群は `references/rules/` にまとめる
- レビュー結果は findings first を維持し、概要は必要最小限に留める

## `scripts/`

追加しない（手順はテキストで足りる。同じ整形・検証を繰り返し自動化したくなったら `scripts/` を足す）。
