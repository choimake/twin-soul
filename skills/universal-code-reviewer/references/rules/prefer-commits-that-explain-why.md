# コミットメッセージには Why を書く

## ねらい

コミットメッセージは、変更の理由（Why）を残す場所にする。
差分を見れば分かる変更内容（What）の羅列だけだと、後から変更理由を追えない。

## チェック観点

- メッセージの主眼が、変更理由・動機・解消したい問題になっているか
- 変更ファイル名や操作の言い換え（「追加する」「修正する」だけ）に留まっていないか
- 複数の理由が混ざる場合、1 コミットにまとめる必要があるか。不要なら分割を提案できるか

## 指摘する基準（境界）

- 差分から自明な What だけで、Why が増えていない場合は改善を提案する
- バグ修正なら「何が壊れていたか」、機能追加なら「何を可能にしたいか」が一文で分かれば指摘しない
- 機械的なスタイル整形のように理由が定型で足りる変更は、短い定型メッセージとする

## 例

### 悪い例（What の言い換え）

```text
fix: update UserService.java
```

変更した事実は分かる。なぜ直したかは分からない。

### 良い例（Why がある）

```text
fix: 権限がないユーザーでも保存できていたため、保存前に WRITE 権限を必須にする
```

## 補足

- 件名には結論を書く。本文が必要なら、背景や影響範囲を短く添える
- 変更全体の動機（Why）はコミットに書く。行の隣の局所判断（Why not / 制約）はコメントに書く。詳細は `write-intentful-comments.md` を参照する
- テストの What とは役割を分ける
