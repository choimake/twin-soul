# コメントには意図を書く

## ねらい

コメントを書くなら「何をしているか」だけでなく、**なぜそうしたか（意図/背景/制約）** を残す。
意図が分かると、後から読む人が変更判断をしやすくなり、レビューのQAも減る。

## チェック観点

- コメントが「処理の説明」ではなく **意図（Why）** を書けているか
- 数値/閾値/分岐条件などに「根拠」がある場合、理由や参照先（Issue/DR/ドキュメント）を残せているか
- 意図が長くなるなら、コード内ではなく **DR/ドキュメント** に寄せるべきではないか

## 指摘する基準（境界）

- コメントが What の言い換えに留まり、**判断材料（制約/根拠/トレードオフ）が増えていない** 場合は削除/置換（命名・分割）を提案する
- 「なぜこの値/分岐なのか」が後から変えにくい箇所（閾値、例外処理、回避策など）は、**短い Why + 参照先** を推奨する

## 例

### 悪い例（What だけで Why がない）

```java
// MAX_CACHE_SIZE を 100 に設定する
private static final int MAX_CACHE_SIZE = 100;
```

コメントが「何をしているか」の言い換えに留まり、なぜ 100 なのか（根拠/制約/背景）が分からない。

### 良い例（Why を書く）

```java
// MAX_CACHE_SIZE を 100 に設定する理由:
// - メモリ使用量を最適化しつつ、頻繁にアクセスされるデータを十分にキャッシュできると判断したため
// - 詳細は運用メモ/Issue（例: Issue #13）に記載
private static final int MAX_CACHE_SIZE = 100;
```

## 補足

- 「読むだけで自明」な処理はコメントを書かず、コードの構造（関数分割/命名）で表現する
- 意図はコードより **寿命が長い**。更新しやすい場所（DR/ドキュメント/Issue）に置く選択も積極的に行う
