# コメントには Why not を書く

## ねらい

コメントには、処理内容（What）や手順（How）の言い換えを書かない。
選ばなかった案や非自明な制約（Why not）を残す。
後から読む人が、現在の形を採った理由を判断できるようにする。

Why not は Why の一種である。コメントで Why を禁止するルールではない。
足りないのは、根拠のない Why と、他案・制約の欠落である。

## 置き場の分担

- 変更全体の動機（なぜこの変更を入れたか）はコミットメッセージに書く。詳細は `prefer-commits-that-explain-why.md` を参照する
- 行の隣のコメントには、その箇所の局所判断（他案を採らない理由、制約）を書く

## チェック観点

- コメントが、コードを読めば分かる What / How の繰り返しになっていないか
- 閾値、例外処理、回避策、意図的な非採用について、判断材料（他案・制約・根拠）が増えているか
- 根拠が長い場合、コード内コメントではなく Issue / DR / ドキュメントへの参照になっているか

## 指摘する基準（境界）

- What / How の言い換えだけで判断材料が増えていない場合は、削除または命名・分割への置換を提案する
- 後から変えにくい箇所（閾値、例外、互換のための回避）では、短い Why not または制約と、必要なら参照先を推奨する
- 「パフォーマンスのため」のように根拠が薄い Why だけの場合は、他案・制約・参照を足すよう提案する
- 他案が無い制約だけの説明（例: API が当該値を返さない）は、判断材料になっていれば指摘しない
- 変更全体の動機だけがコメントにあり、局所判断が無い場合は、コミット側へ移すか、局所の Why not / 制約を足すよう提案する

## 例

### 悪い例（What / How の言い換え）

```java
// MAX_CACHE_SIZE を 100 に設定する
private static final int MAX_CACHE_SIZE = 100;
```

コメントが設定内容の繰り返しに留まっている。100 以外を採らなかった理由が分からない。

### 悪い例（根拠の薄い Why）

```java
// パフォーマンスのため 100 にする
private static final int MAX_CACHE_SIZE = 100;
```

Why はある。他案や制約が無く、後から値を変えられない。

### 良い例（Why not がある）

```java
// 無制限キャッシュはメモリ逼迫の前例があるため上限を置く。
// 50 ではヒット率が足りず、200 ではピーク時に OOM したため 100 とする。詳細は Issue #13。
private static final int MAX_CACHE_SIZE = 100;
```

### 良い例（制約だけの Why。指摘しない）

```java
// この API は total を返さないため、件数は別クエリで取得する
int count = countRepository.countByUserId(userId);
```

他案の列挙は無い。制約が書かれており、判断材料になっている。

## 補足

- 読むだけで自明な処理にはコメントを書かない。How はコードの構造と命名で示す
- Why not の詳細が長い場合は、DR / ドキュメント / Issue に置き、コメントには要約と参照だけを残す
