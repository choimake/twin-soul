# コメントには Why not を書く

## ねらい

コメントには、処理内容（What）や手順（How）の言い換えを書かない。
選ばなかった案や非自明な制約（Why not）を残す。
後から読む人が、現在の形を採った理由を判断できるようにする。

## チェック観点

- コメントが、コードを読めば分かる What / How の繰り返しになっていないか
- 閾値、例外処理、回避策、意図的な非採用について、他案を採らなかった理由が書かれているか
- 根拠が長い場合、コード内コメントではなく Issue / DR / ドキュメントへの参照になっているか

## 指摘する基準（境界）

- What / How の言い換えだけで判断材料が増えていない場合は、削除または命名・分割への置換を提案する
- 後から変えにくい箇所（閾値、例外、互換のための回避）では、短い Why not と参照先を推奨する
- 「なぜそうしたか」だけがあり、比較対象や制約が無い場合は、他案・制約（Why not）を足すよう提案する

## 例

### 悪い例（What / How の言い換え）

```java
// MAX_CACHE_SIZE を 100 に設定する
private static final int MAX_CACHE_SIZE = 100;
```

コメントが設定内容の繰り返しに留まっている。100 以外を採らなかった理由が分からない。

### 良い例（Why not がある）

```java
// 無制限キャッシュはメモリ逼迫の前例があるため上限を置く。
// 50 ではヒット率が足りず、200 ではピーク時に OOM したため 100 とする。詳細は Issue #13。
private static final int MAX_CACHE_SIZE = 100;
```

## 補足

- 読むだけで自明な処理にはコメントを書かない。How はコードの構造と命名で示す
- Why not の詳細が長い場合は、DR / ドキュメント / Issue に置き、コメントには要約と参照だけを残す
