# Pragmatic Architect 判断知識

この資料は `pragmatic-architect` skill の判断知識をまとめたものである。`SKILL.md` は使い方に留め、判断基準・質問生成ルール・用語定義はこの資料を起点にする。

## 用語集

日本語を見出しにする。`Core` と `Details` は用語として本文でも使う。description の Legacy Baseline / Allowed Exceptions は trigger 用の別名で、手順と草案の見出しは日本語にする。

- **Core**: プロジェクトの長寿命な中核。ビジネスルール、ドメインモデル、データ構造など、交換しない前提で守るもの。
- **Details**: UI、DB、フレームワーク、外部 API など、交換可能な実装詳細。Core に依存してよいが、Core が Details に依存してはならない。
- **依存方向**: Details から Core への一方向の依存を守る方針。Core が Details に依存する逆方向は汚染とみなす。
- **汚染例**: Core が Details に依存している具体的な箇所。既存コードから証拠として抽出する。
- **許容する例外**: 将来も意図的に許可する戦略的近道。費用対効果やトレードオフを合意したうえで明示する。
- **棚上げする既存負債**: 既存負債として当面は違反扱いを保留する範囲。許容する例外とは異なり、将来的には解消を目指すが、今は監視対象から外す。
- **未決事項**: 合意待ちで確定できない論点。草案に残し、次の対話で解消する。

## 構造の違う仮説 2 案

確認質問の前に、構造の違う仮説を 2 案出す。1 案だけで草案へ進まない。ユーザー合意なしに実装へ進まない。

2 案に数える:

- Core の置き場所が違う（例: ドメインを `services/` に置く / 永続化モデルを Core とみなす）
- 依存の切り方が違う（例: 今は直接依存を許容する例外にする / アダプタを挟んで分離する）
- 負債の扱いが違う（例: 今期は棚上げする / 境界だけ先に合意する）

2 案に数えない:

- 同じ境界の言い換え
- 同じ形の点修正（名前だけ変える、同じ層にファイルを足す）
- 「きれいにする / もっときれいにする」

捨てるサイン（同じ形が繰り返されたら Core の切り方を疑う）:

- 同じ形の回避が、無関係な箇所に繰り返し出る
- 無関係な例外分岐が、同じ逃げ方を要求する
- 呼び出し側が内部規則を知らないと使えない
- 共有しない前提なのに、毎回ロックやグローバル状態が要る

サインが出たら、今の Core 仮説を捨てて 2 案を作り直す。確認ループは残す。

## Core の判定基準

Core とみなす条件:

- プロジェクトの存在理由に直結する概念やルール
- フレームワークや UI を差し替えても残るべきロジック
- 複数の Details から参照されるが、Details の変更に引きずられてはならないもの
- 変更頻度が低く、変更時の影響範囲が広いもの

Core とみなさない条件:

- 特定のフレームワークや DB に固有の実装
- 表示形式、通信プロトコル、永続化手段に紐づくコード
- 外部サービスの SDK やアダプタ

判断に迷う場合は「このコンポーネントを別のフレームワークに移植するとき、書き直さずに持っていけるか？」を基準にする。持っていけるなら Core 候補、持っていけないなら Details 候補。

## Details の判定基準

Details は交換可能性で判定する。

- UI コンポーネント、ビューレイヤー
- データベーススキーマ、ORM、永続化アダプタ
- HTTP フレームワーク、ルーティング
- 外部 API クライアント、SDK ラッパー
- 認証プロバイダのアダプタ
- ログ、メトリクス、監視の実装

Details が Core のインターフェースを実装する形が理想だが、初期定義では理想形の押しつけより現状の事実整理を優先する。

## 情報源の優先順位

この優先順位は現状の事実を把握するためのものであり、最終的に何を Core として守るかの判断権は人間にある。skill は事実に基づくトレードオフ質問を通じて人間の判断を引き出し、合意結果を `.architecture-core.md` に落とす。

1. **現行コード**: 実際に動いている実装が最も信頼できる事実
2. **テスト**: テストが守っている振る舞いは、意図された Core の手がかり
3. **最近のコミット・PR**: 直近の変更意図が読める
4. **README・設計ドキュメント**: 意図を示すが、古い可能性がある
5. **人間へのインタビュー**: 暗黙知を引き出すが、理想論に寄りやすい

古いドキュメントへの対処:

- ドキュメントの記述とコードの実装が食い違う場合、コードを事実として優先する
- ドキュメントの意図が現行コードで実現されていないなら「意図は X だが、現状は Y」として両方を提示する
- 偶然そうなった実装（歴史的経緯で残っているだけ）と、意図的な設計判断を区別するために、コミット履歴やテストの有無を確認する

## Core 汚染の具体例

汚染とは、Core が Details の知識を持ってしまっている状態を指す。

典型パターン:

- ドメインモデルに ORM のアノテーションやデコレータが付いている
- ビジネスロジックの中で HTTP レスポンスコードを直接返している
- Core のモジュールが特定の DB クライアントを直接 import している
- ドメイン層のデータ構造がフレームワーク固有の基底クラスを継承している
- ビジネスルールの分岐に UI の表示条件が混入している

汚染の検出方法:

- Core 候補のモジュールの import 文を確認し、Details に分類されるモジュールへの依存がないか調べる
- Core のテストが、DB やフレームワークの起動なしに実行できるか確認する
- Core のモジュールを別プロジェクトにコピーしたとき、依存エラーが出るか想像する

## 許容する例外 と 棚上げする既存負債 の違い

| 観点 | 許容する例外                                               | 棚上げする既存負債                                      |
| ---- | ---------------------------------------------------------- | ------------------------------------------------------- |
| 意図 | 戦略的に許可する近道                                       | 既存負債として当面保留する範囲                          |
| 将来 | 維持し続ける前提                                           | 将来的には解消を目指す                                  |
| 合意 | 費用対効果を議論して意図的に決める                         | 現時点で手を入れるコストが見合わない                    |
| 例   | 「この小規模サービスでは DI を省略し、直接依存を許可する」 | 「旧モジュール X は密結合だが、今期のリファクタ対象外」 |

判定の流れ:

1. 違反箇所を発見する
2. 意図的にそうしているのか、偶然そうなったのかを確認する
3. 意図的で、今後も維持するなら → 許容する例外
4. 偶然または歴史的経緯で、将来直したいが今は手を入れないなら → 棚上げする既存負債
5. 判断がつかないなら → 未決事項に入れる

## 確認質問の生成ルール

質問を返す前に必ずすること:

- ディレクトリ構造の解析結果を箇条書きで提示する
- 密結合や汚染の具体例を、ファイルパスつきで箇条書きにする
- Core / Details の仮の分類を、構造の違う 2 案として提示する

質問の形式:

- オープンクエスチョン（「どうしたいですか？」「何が重要ですか？」）は禁止
- 既存コードやドキュメントから推測した事実を先に提示し、その事実に対する判断を問う
- 「速度優先で合法化するか / 保守性優先で負債として扱うか」のように二択または三択のトレードオフに寄せる
- 各質問に、具体的なファイルパスまたはモジュール名を必ず含める

質問の例:

- 「`src/models/user.py` が SQLAlchemy の `Base` を継承しています。これを Core とみなして ORM 依存を許容する例外にするか、Details に寄せて将来分離する前提で棚上げするか、どちらが現実的ですか？」
- 「`lib/api/client.ts` が `domain/order.ts` を直接 import しています。この依存を意図的に維持するか、アダプタ層を挟んで分離するかで、初期コストが変わります。現時点のチーム規模を考えると、どちらを選びますか？」

反論と妥協案:

- ユーザーの理想論が現状と大きく乖離するときは、反証となる事実を示してよい
- 「全部きれいにしたい」に対しては、現状の密結合箇所の数とリファクタコストの概算を示し、段階的な妥協案を提案する
- 妥協案は棚上げする既存負債として切り出して提示する

## 足りないときの扱い

- README がない、または空の場合: ディレクトリ構造とエントリポイントから仮説を立てる
- テストがない場合: コードの実装だけから Core 候補を推測し、その不確実性を明示する
- 設計ドキュメントがない場合: コミット履歴とコードの構造から意図を推測する
- コードベースが小さすぎる場合: Core / Details の分離自体が過剰でないか確認し、「現時点では分離不要だが、成長時に見直す」という判断も選択肢に含める
- 情報が足りず判断できない場合: 不明点を未決事項に入れ、追加で必要な情報を具体的に示す

## 将来の拡張方針

初期定義（`.architecture-core.md` の草案作成）のみを扱う。将来的に既存草案の違反検出、リファクタ計画、個別判断の費用対効果比較への拡張を想定するが、本実装は後続の plan で扱う。
